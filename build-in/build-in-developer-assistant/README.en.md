# Project Assistant

Assistant is one aggregate project: `main` is the default Conversation entry and `studio-control` is the embedded Workflow entry under `studio-control/`. They share one projectId, dependency set, version and installation. Studio discovers and calls control tools through this project’s `mcp --entry studio-control` on demand, without installing or registering another project. Open the Assistant project root in Studio to run the Workflow entry directly.

Studio's independent built-in assistant runs on the Core Agent runtime using the SteamHarness Server system AI configuration supplied by its host. The host supplies its working directory and authorized roots through `STEAMHARNESS_DEVELOPER_ASSISTANT_WORKDIR` and `STEAMHARNESS_DEVELOPER_ASSISTANT_WORKSPACE_MANIFEST`; editor projects and conversation parameters cannot expand that scope.

The host defaults to `vscode`, or can explicitly set `STEAMHARNESS_DEVELOPER_ASSISTANT_HOST=vscode`. The assistant offers Core coding tools, bundled skills, host-authorized account memory and file/browser resource cards. When Studio injects a control connection, Studio Control's standard MCP adds workspace state, diagnostics, aggregate entry queries, file navigation, installed themes, terminals and common views. Editor actions follow tool permissions and Build/Plan approvals; state, diagnostic and entry reads are automatically approved. `get_entries` returns the aggregate project identity, default entry and registered entry IDs, types and names. Database spaces require separate host approval and a binding for each consuming entry. Coding remains available without a control connection. Generic configuration tools manage every project type; legacy Desktop Control is not connected. With a control connection, `get_kanban_diagnostics` reads open local Kanban previews, bridge routing and failures, and explicitly read-only page methods so the assistant can verify actual readiness such as `imageReady`; arbitrary scripts and mutating page methods are unavailable.

Permission supports `read-only`, `workspace` and `auto`, defaulting to `auto` (Auto approve). Both conversation messages and OpenAI requests use this default when no policy is specified. Read-only hides writing and command tools. Workspace limits file and search tools to authorized roots; shell commands are not sandboxed. Auto approves permissions that are not explicitly denied, allowing reads, edits and searches in any directory accessible to the process, including absolute paths outside the workspace. The prompt and Studio Control follow the run's policy, and `studio_state` reports the effective policy and path access. Core manages Build/Plan modes; Plan can investigate, ask questions and wait for approval.

This repository maintains `skills/steamharness-generator`. The `skill` tool lists and reads it on demand without installing it globally. SteamHarness tasks first read the skill and relevant API references; other tasks use only relevant skills. Follow `nextOffset` until `truncated: false` to read every skill page; retry with a smaller `limit` if an outer layer truncates output. Stop only an operation whose required file remains missing, denied or unreadable after recovery, and continue independent work. Complete implementation and relevant checks in the same run, correcting recoverable tool errors. Read-only subagents include `skill` and inherit the current model and credentials unless an explicit allowlist permits an override. File cards use `target.filePath` and omit `preview`.

Open **Project information → Skills** to see actual skill names, counts and sources. Select a skill to preview its complete `SKILL.md` and Markdown source in read-only mode, with no enable or auto-approval controls. The assistant reads these guides through the `skill` tool: `{"action":"list"}` returns names, descriptions and files, `{"action":"read","skill":"steamharness-generator"}` reads the guide, and `{"action":"read","skill":"steamharness-generator","path":"references/task-map.md"}` reads a reference relative to its skill directory. Reading a script returns its text; the assistant uses the corresponding tools to execute its steps. See [createSkillTools](../../docs/en/core-api/create-skill-tools.mdx) for parameters, results and reading limits.

Studio's built-in assistant uses a fixed distributed identity. Users do not need to create a personal Server project or apply for a new ID. The application checks area hides after success. Ordinary projects cannot skip registration by copying the ID or declaring themselves built-in. Server AI remains authorized through the current account.

Assistant Knowledge, KV and memory are separate from the assisted project's data. Run-scoped Knowledge and KV tools are not offered, avoiding writes to an unrelated store. Server stores private account memory for recall across devices: lasting personal preferences are global, project decisions belong to the personal project scope, and ordinary directories use independent host-registered identities. Memory never stores credentials or transient progress. Session history and pending turn submissions remain in the host user data directory. Sign in again for independent memory authorization; missing authorization never falls back to the old database. Settings → Memory provides browsing, editing and forgetting; the Skills page previews the read-only steamharness-memory guide. Business databases require declared needs and explicit host approval and binding.

This project lives at `build-in/build-in-developer-assistant` in the monorepo and references the harness and the CLI through `link:../../harness` and `link:../../cli`. Studio builds the bundled assistant from `build-in/build-in-developer-assistant` and can resolve development dependencies from this repository. Verify changes with `pnpm typecheck`, `pnpm test`, `pnpm coverage`, `pnpm build` and `git diff --check`. Studio documents its integration in `docs/workflow-workstation.md`.
