# 编码规则:

- 写完代码之后需要提交到远程去
- 需要遵循 DESIGN.md 中的设计
- 高频事件触发的界面刷新必须防抖，保留已有内容并忽略过期结果，避免重复加载和闪烁。
- 底层支持优先, 优先从 cli , core 这些底层中处理 , 而不是在界面上进行特殊处理

## 自动化测试规则:

- Studio CI 测试暂时停用：`.gitlab-ci.yml` 的 `workflow.rules` 禁止创建流水线，日常测试和完整测试均不触发，包括推送及手动/API 触发。只有用户明确要求恢复后才能重新启用 CI 测试入口；不得自行触发或重跑 CI 测试。

### 日常测试

- 默认执行日常测试：按改动范围运行单元测试、类型检查及扩展构建，完整静态检查入口为 `npm run check` 和 `npm run build:extension`。CI 测试暂停期间不自动执行 `framework-check`。
- 日常测试必须在后台完成，不占用用户的系统鼠标、前台窗口、键盘焦点或剪贴板。可按需执行已确认使用 `headless: true` 的浏览器测试；不能仅凭脚本名称包含 `ui` 就认定它是无头测试。
- 不得在用户正在使用的本机桌面启动 Electron、带窗口的浏览器、原生菜单或系统剪贴板测试，也不得针对本机可见窗口调用 `bringToFront()`、`app.focus({ steal: true })` 或系统输入控制来验证界面。需要这些能力时转入完整测试；独立无头浏览器内部的页面焦点不属于系统窗口焦点。

### 完整测试

- 完整测试在 GitLab CI 的 `linux` 标签 runner 上执行。当前对应 runner 为 `win-linux`（可通过 `~/.ssh/config` 中的同名 SSH Host 检查环境），使用 Linux 的 Xvfb 虚拟显示和独立窗口管理器运行真实 Electron；窗口、焦点及剪贴板操作都留在远端测试环境。
- 用户明确要求恢复 CI 测试入口后，先提交并推送到本次任务的目标分支，再通过 `glab ci run --repo http://yuhe.space:7201/workflow/studio --branch <目标分支> --variables STUDIO_FULL_TESTS:1` 触发 `full-test`。显式指定仓库地址，避免 SSH remote 与 GitLab API 端口不同导致 glab 匹配失败。这里的 `linux` 是 CI runner 标签，不是 Git 发布 tag；不得为测试创建发布 tag。
- 完整测试包括类型检查、全部单元测试、扩展及 VS Code 构建、扩展宿主测试，以及当前已提交的自包含浏览器和桌面 UI 回归。测试使用隔离的数据目录，串行执行并保存各项结果、截图和日志。
- 完整测试优先控制内存峰值，可以接受较长耗时。按 runner 的现有资源配额限制安装和构建并发及单进程内存，交付时检查包括子进程在内的实际内存占用和内存回收压力。
- CI 下载必须复用 runner 的持久缓存，包括 Node 工具链、npm/pnpm 包、node-gyp 头文件、Electron 和 Playwright 浏览器。node-gyp 启用 `npm_config_ensure=true`，按目标版本和缓存安装版本检查后复用；不得为重跑测试清空有效缓存。
- 桌面 UI 用例通过隔离测试扩展等待 Studio 扩展激活完成，再执行命令和界面交互；CI 的启动等待上限为 5 分钟。低资源 runner 上不得靠提高资源配额解决启动时序超时。
- Electron 使用 Studio 根目录的 `npm run electron`，与本机开发共用 `config/downloads.json` 的镜像、重试、官方源回退和上游 SHA-256 校验；不得直接调用上游下载脚本绕过项目策略。CI 复用持久缓存，下载和校验流式处理，避免整包载入内存。
- 执行前确认 runner 在线、实际 runner 标签和机器身份正确，Node 满足 `.nvmrc`，并具备原生构建依赖、Xvfb、窗口管理器、浏览器及对应的 Linux Electron。Shell runner 不会应用 CI 的 `image:`，不能把镜像声明当作环境已就绪的证据。
- 真实服务、真实模型、外部样例文件及 macOS 专有行为需要相应环境和测试资料；缺少条件时必须明确报告未覆盖项。不得将 Linux 回归或静态检查通过表述为这些用例也已通过。
- 通过 `glab api` 检查本次提交对应的 pipeline、job、实际 runner 和日志，并等待终态。创建流水线、排队或只通过静态检查均不等于完整测试通过；交付时提供流水线链接、测试结果及未覆盖项。

## VS Code 国际化规则:

- 新增或修改的用户可见文案（界面、命令、菜单、标签、工具提示、空状态及错误提示）至少支持英文（en）和简体中文（zh-cn），并跟随 VS Code 当前显示语言；未支持的语言或缺失的翻译回退到英文。
- 使用项目现有国际化机制及翻译目录：扩展声明使用 `package.nls.json` / `package.nls.zh-cn.json`，运行时使用 `@vscode/l10n` 及对应翻译文件，禁止硬编码单一语言的用户可见文案。
- Webview 和嵌入的 CLI 页面必须同步 VS Code 宿主语言，确保侧栏、底部面板及项目运行界面的语言一致。
- 用户输入、项目自定义内容、执行结果及日志保留原文；项目声明中提供了多语言名称或描述时，按当前显示语言选择展示。
- 涉及界面文案的改动，交付前验证中英文两种显示语言，包括命令名称、工具提示、空状态及错误提示，避免英文界面混入硬编码中文。
