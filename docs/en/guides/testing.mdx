# Automated Testing

Each SteamHarness repository installs dependencies and runs its own quality gates. Offline, reproducible tests are the first layer of confidence and do not connect to production PostgreSQL, real OSS, LLM, GitLab, Electron, or a remote server. Server's PostgreSQL integration suite uses a disposable isolated PostgreSQL 15 container. Real-environment checks must be explicitly enabled in the affected repository.

Run every command below from the corresponding repository root. Every repository maintains `dev`, `alpha`, and `main`, and day-to-day work happens on `dev`; the branch model does not change the local gates, only the release-channel reference rules (see [Compatibility](releases/compatibility.mdx)).

## Test Layers

| Repository | Command | Purpose |
| --- | --- | --- |
| Core | `pnpm typecheck && pnpm test && pnpm test:scripts && pnpm coverage && pnpm build && pnpm test:agent-dist` | Checks Core APIs, scripts, the npm build, and built artifacts; ordinary tests cover runtime behavior and minimal temporary fixtures. |
| CLI | `pnpm typecheck && pnpm test && pnpm test:scripts && pnpm coverage && pnpm build` | Checks local CLI commands and `steamharness workspace`. Before a release, also run `pnpm pack --pack-destination .release`. |
| Studio | `npm run check && npm run build:extension` | Checks the workstation extension and its offline tests. |
| Server | `pnpm typecheck:all && pnpm test && pnpm coverage && pnpm build:all` | Checks both the Server API and the repository's `web/` management UI. |
| Shared | `pnpm typecheck && pnpm test && pnpm test:scripts && pnpm coverage && pnpm build` | Checks shared source packages and the source bundle consumed by hosts. |
| Docs | `node scripts/validate-docs.mjs && node --test scripts/__tests__/*.test.mjs` | Checks paired navigation, links, and OpenAPI content. |
| Each built-in project | `pnpm typecheck && pnpm test && pnpm coverage && pnpm build` | Independently checks Bot, Codex, OpenCode, Developer Assistant. |

## Add Tests for New Code

- For `src/**` in the Core repository, add Core unit tests and npm exports or pack regression tests first.
- For `src/**` in the Server repository, cover routes, storage, permissions, and error codes, using stub storage to stay offline.
- For `src/**` in the CLI repository, extract argument parsing, path handling, output formatting, and error codes into importable helpers, then cover them with Vitest.
- For `web/**` in the Server repository, cover API clients, routing, loading, empty, error, disabled, and critical component interaction states.
- For `run-workspace-input/**` in the Shared repository, cover input, conversation, attachments, Markdown and output items, image preview, Enter-to-send, menus, title locking, and responsive states.
- Test Core nodes and runtime behavior in `src/__tests__/*.test.ts` with `node:test`, included in regular tests and coverage. Analyze structure directly from source snippets.
- For a built-in project, cover entry parameters, execution results, failure paths, and structure snapshots in that project's own `__tests__/` directory.

## Test Fixtures

Construct nodes, Workflow definitions, and in-memory contexts directly for common capabilities. Assert pause and resume, streaming cancellation, knowledge sharing, and authorization without depending on business projects.

When loaders, entry discovery, Kanban HTML, packaging, or CLI execution need a filesystem, generate minimal manifests and source files in a system temporary directory and clean them up after each test. Reuse existing fixture helpers and repository dependencies. Do not maintain permanent test projects or separate lockfiles, or install dependencies for fixtures. CLI command tests belong to the CLI suite.

Mock external dependencies by default: use test LLM providers and temporary file contents. Real SDKs, remote services, and external processes require explicitly enabled integration tests.

## Cross-Repository Changes

After a Shared change passes its own gates, run the corresponding gates in every affected Server, Core, or CLI consumer. A Core API change should also verify consumer tests in CLI, Server, and affected built-in projects; a CLI change should verify Studio and CLI command regressions. Repositories prepare shared source from a sibling checkout when available and otherwise fall back to the committed `vendor/shared`, so CI does not depend on an outer multi-repository directory.

Checks against a real Server, database, LLM, Electron window, or browser run only when explicitly enabled and do not replace the offline gates above. If the required gates still cannot run after repairing the environment, record the blocker, impact, and alternative verification.
