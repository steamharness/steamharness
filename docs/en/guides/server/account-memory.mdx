# Account memory

Server stores account memory across devices. Studio and Server Web expose it under **Settings → Memory**. CLI Web exposes **Project information → Global memory**, restricted to personal global and the current project or directory. Core capabilities determine whether this tab exists: disconnected or disabled memory is hidden; temporary outages retain an error state.

Ordinary projects default to memory off; the built-in Assistant opts in. Open the current configuration under **Project information → Project configurations**, change **Project memory** and save. The next run uses this setting for global/current recall, saving and tools. Turning it off retains existing records, which remain manageable in account settings. The account switch is separate and must also allow memory.


## Use and privacy

- Personal global memory contains explicit lasting preferences, including instructions about response language and style across projects, whether upstream classifies them as `persona` or `instruction`. Project conventions and decisions stay in personal project memory. Project-only instructions and uncertain facts are never promoted to global.
- All records are private to the account, including records for the same project. Directories use random host-registered identities; equal folder names on different devices do not merge.
- Ask the assistant to remember immediately, edit or forget, or use the panel. Edits require the current version; conflicts preserve the draft and request a refresh.
- Deleting a conversation does not forget long-term memory. Clearing a scope requires separate confirmation and prevents older turns from recreating cleared records.
- Revoked project access exposes only locked counts and allows clearing. Bodies, summaries, sources and search hits remain hidden until access is restored.
- The read-only Skills tab previews the complete `steamharness-memory/SKILL.md`. Memory and automatic saving controls belong to the Memory panel.

Account changes and sign-out clear panel content and discard stale responses. Lists use server filtering and cursor pagination; details show full text, sources, versions and update times. Panels support English, Chinese and the host theme. The CLI dialog retains its viewport-constrained 1040×720 size.

Studio settings use a continuous surface with descriptive preference rows and compact switches on the right. Scope and source filters lead into the memory list, with details shown on selection. Loading, empty, unconfigured and temporary-error states stay distinct without resizing the panel.

Studio checks account status silently in the background. Routine profile and system AI connection updates preserve the memory panel, including filters, details, focus and unsaved drafts. Switching accounts or servers, or an expired sign-in, immediately clears previous content and discards stale responses.

## Service configuration

Memory Service requires Node 22.13+, SQLite FTS5 and a persistent writable volume. It pins the reviewed TencentDB-Agent-Memory revision `ecc01a545da0b2ac6cae2f0f0af0d39d41469793` with its MIT license, provenance and replayable patch. It does not use upstream's private service extensions. Only Memory Service loads native jieba; Core, CLI and Studio do not.

| Process | Setting | Purpose |
| --- | --- | --- |
| Memory Service | `STEAMHARNESS_MEMORY_SERVICE_TOKEN` | Internal credential, at least 32 characters |
| Memory Service | `STEAMHARNESS_MEMORY_DATA_DIR` | Persistent directory for account SQLite files |
| Memory Service | `STEAMHARNESS_MEMORY_MODEL_BASE_URL` | Dedicated extraction model's OpenAI-compatible `/v1` endpoint |
| Memory Service | `STEAMHARNESS_MEMORY_MODEL_API_KEY` | Extraction credential held only by this service |
| Memory Service | `STEAMHARNESS_MEMORY_MODEL` | Administrator-selected extraction model |
| Server | `STEAMHARNESS_SERVER_MEMORY_URL` | Internal Memory Service URL |
| Server | `STEAMHARNESS_SERVER_MEMORY_TOKEN` | Matching internal credential |
| Server | `STEAMHARNESS_SERVER_MEMORY_DISABLED=1` | Disable memory while conversations continue |
| Development supervisor | `STEAMHARNESS_SERVER_MEMORY_AUTOSTART=0` | Disable local autostart while retaining external-service access |

Manual saves and BM25 retrieval work without an extraction model or embeddings. Automatic extraction has no tools. It processes only durable completed turns containing user text and the final answer, excluding reasoning, raw tool results and recalled injection. Jobs attempt automatically at most three times, with failure status and manual retry in the panel.

Without an extraction model, new turn submissions return `accepted: false` without creating guaranteed-to-fail jobs. Temporary service failures return 503 so the host retains pending turns for retry after recovery. Existing jobs keep their stable IDs.

Extraction jobs distinguish queued work, running work, saves paused by expired authorization, and extraction service failures. After the original login is revoked, the account can explicitly retry using its current login to authorize the original scope. Background workers never switch logins automatically. Restore project access before retrying a locked scope, and enable account memory and automatic saving first. Retries preserve the original task ID, scope and extraction snapshot, so forgotten, cleared or manually superseded content cannot be recreated.

### Automatic development startup

On a development branch, `pnpm -C server dev` and `pnpm -C server start:local` start a local Memory Service and wait for its health check before starting Server. No separate terminal or service build is needed. The supervisor assigns a free loopback port and generates an internal credential. Server hot reloads reuse that service; exiting stops it. IPC disconnection also stops the service if its supervisor is killed.

Configuration follows Server's `.env`, with inherited environment values taking priority. SQLite persists under `<Server data directory>/memory` by default. Set `STEAMHARNESS_MEMORY_DATA_DIR` to override it; relative paths use the Server root. Restarts preserve records. `STEAMHARNESS_MEMORY_PORT` can pin the port. A busy port or local startup failure is reported while Server continues running.

Automatic startup runs in the development launcher. Running `tsx src/index.ts` directly or retaining a process started with an older command does not start Memory Service. After updating the sources, stop that process and run one of the development commands above.

```sh
# Disable local autostart only; an explicitly configured external service still works
STEAMHARNESS_SERVER_MEMORY_AUTOSTART=0 pnpm -C server dev

# Disable all memory access and local autostart
STEAMHARNESS_SERVER_MEMORY_DISABLED=1 pnpm -C server dev
```

Both switches can also be set in Server's `.env`. An explicit `STEAMHARNESS_SERVER_MEMORY_URL` reuses the external service with its matching `STEAMHARNESS_SERVER_MEMORY_TOKEN`; the supervisor neither starts nor stops that external process. Production continues to use independent deployment. Main branches, tags and detached checkouts never autostart the source service.

### Independent deployment

From the repository root:

```sh
pnpm --filter @steamharness/memory-service build
pnpm --filter @steamharness/memory-service start
```

The source also includes `memory-service/compose.yaml`. Restrict its port to loopback or an internal network. Keep the credential and volume inaccessible to project processes.

## Login and authorization

Password and device sign-in issue an independent memory management credential. Studio account settings can also reuse a valid account login session held by the host, so browsing memory does not require another sign-in. Account verification is offered only when no valid authorization remains; an unconfigured or temporarily unavailable service does not ask users to sign in again. Project API keys cannot manage account-wide memory. Only the trusted host retains management credentials and session cookies. Agents receive a five-minute grant for global plus the current project or directory, and cannot choose account identities, other projects or issue grants.

Every request and extraction commit rechecks account status, parent login and project access. Revocation or account disabling stops access. Planning, read-only runs and subagents cannot save. Core makes no memory promise without a binding. Legacy database memory APIs remain available; the built-in assistant does not implicitly fall back, dual-write or migrate old records.

## Storage and recovery

PostgreSQL holds the persistent Server instance identity, preferences, scopes, credentials, jobs and operation receipts. Account SQLite files hold pending L0 turn text, memory bodies, sources, FTS5 indexes, atomic receipts and deletion suppression. Completed L0 text is removed. Hosts retain only pending submission records, not a second authoritative cloud copy.

Pause memory traffic and workers for a coordinated backup of PostgreSQL and the service volume. `memory-service/scripts/snapshot.mjs` uses `VACUUM INTO` to include WAL data. Preserve `memory_instance` when restoring; changing it changes account namespaces. Verify recovery on an isolated database and volume. Do not copy an active SQLite main file by itself.

Clear increments scope generations; forget retains content fingerprints and suppressed source IDs. Manual changes invalidate earlier extraction snapshots. SQLite atomically commits bodies and receipts, so network retries do not duplicate writes. Disable memory before rolling back code and preserve tables, volumes and suppression data.

Responses use `errCode / errMessage / data`. See [OpenAPI](/en/openapi/steamharness.openapi.yaml) and the [Core account memory API](/en/core-api/account-memory).
