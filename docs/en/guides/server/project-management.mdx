# Project management

Open project details in Server Web, then choose members, versions, configuration, or databases. Entries share a project version; membership and data-resource grants are managed separately.

The aggregate entry list displays each entry’s `projectCard` icon, foreground and background. These properties live in entry declarations and travel with source uploads and version snapshots. Entries have no independent versions; the aggregate owns the root version.

## Project avatars

Project lists, details, and settings display avatars from `projectCard.icon`, `iconColor`, and `iconBackgroundColor`. New projects without an avatar use their project type's icon with randomly generated, saved foreground and background colors. Their contrast ratio is at least 4.5:1. Refreshing the page or reconnecting an existing project does not generate new colors.

Older projects without avatar metadata use their project type's default icon and colors. `iconUrl` remains readable for compatibility, while these views consistently use the icon and colors.

Click a project list avatar to open its details, or a standalone detail avatar to preview it. User avatars in member and uploader lists open the currently visible profile information. Click the avatar inside that dialog or the preview avatar in user management to view a larger image. The account menu avatar opens its menu, while the personal profile avatar selects an upload. Dialogs support keyboard dismissal and return focus to their trigger.

## Fixed roles

Accounts are ordinary users or system administrators. Business access is assigned per project or group using four fixed roles.

| Role | Cumulative capabilities |
| --- | --- |
| `guest` | Read projects, published versions, authorized knowledge resources, project files and previews; download published source to run locally. |
| `developer` | Edit drafts, upload, publish and write Server authorized knowledge resources and project files. |
| `maintainer` | Manage project information, icons, visibility and official configurations; manage guests and developers. |
| `owner` | Assign every role, manage owners, delete projects and transfer ownership. |

Cookie and API key requests use current account status and memberships. Revocation, disabling an account or making a public project private affects subsequent requests immediately, including previews. Local execution still requires grants for the database or knowledge base being accessed; project membership does not directly grant resource access. Personal configurations remain available within published field rules.

## Groups and subgroups

Open Groups in the sidebar to create a top-level group or navigate its projects, subgroups and breadcrumbs. A project belongs to one group or is an ungrouped personal project. Permission groups organize access; aggregate entries belong to the same project.

Any signed-in user can create a personal project or top-level group and become its owner. Group developers may create projects and maintainers may create subgroups. Their creators retain inherited roles without automatic promotion.

Effective access is the highest direct project role or role inherited from the containing group and every ancestor. Lower levels cannot reduce inherited access. Member pages show direct and effective roles with links to the source group. Removing direct membership preserves inherited permissions.

Directories and member lists search and paginate authorized records on the Server. A public project neither grants group membership nor exposes private projects in the same group.

## Members, invitations and requests

Maintainers may grant guest or developer roles and manage users whose effective role is below maintainer. Owners manage every role. Invitation acceptance and request approval recheck current permissions and preserve existing higher roles. Membership invitations expire and are single use; recipients must sign in. Account invitations and password setup are separate from project and group invitations. Server does not send email.

Project and group invitation lists follow the roles the caller can grant: maintainers see guest and developer invitations, while owners and system administrators see every role. System administrators can also approve access requests with an admin key.

Public projects grant every signed-in user guest access without inserting membership records. Private projects accept access requests through published-version share links; approval by a maintainer or owner adds the requester as a guest. Source downloads no longer use separate grants. Revoke approved access through the member page and inspect inherited sources.

Top-level groups and personal projects retain at least one active owner, protected by transactions. Group resources may inherit owners. Transfers require owner access to the resource, its source group when present and its destination. Cycles are prohibited. Only empty groups may be deleted; move their projects and subgroups first.

## Source and versions

Server assigns a fresh aggregate UUID on creation and cloning, registering `entries`, `defaultEntry`, metadata and ownership before source upload. Entries can then request spaces; approval and binding are required for data access. Static previews and publication require source upload.

Uploads only extract, statically validate and save files. Server never installs dependencies, builds or executes uploaded code. Failures preserve drafts and published versions. Publication saves an immutable snapshot and updates `latest`; duplicate versions return `409`.

Release uploads preserve compiled entries and the project version. Draft names, avatars, and declarations use the current Server project metadata. Server validates the file inventory after applying that metadata before allowing publication.

The v2 `structure.json` format encodes internal structure while keeping project and entry summaries in plain text. Server decodes and validates this data statically without executing project code. After publishing configuration and attachments, it compacts JSON again and updates the download inventory.

A developer upload cannot modify management metadata or ownership. Guests download published versions; draft reads require developer access. Archives exclude KV, PersistentValue, SQLite, environment files and CLI credentials.

## Entries and data resources

All aggregate entries share a project version, source archive and installation unit; configurations are entry-scoped. Accounts explicitly create, grant, migrate and bind relational resources. Knowledge bases use independent knowledgeBases declarations and root alias-to-UUID mappings, with STEAMHARNESS_PROJECT_CONFIG deployment overrides. Membership protects project source and configuration; data access checks the relevant account resource grant and effective binding. Binding grants no access; deleting a project retains independent resources.

## System administration and audit

User administration sets account status and system administrator identity. System administrators have global management access and handle accounts, system audit and administrative tools. System audit is administrator-only, with credentials redacted.

HTTP responses expose `access: { effectiveRole, sources, capabilities }`. Clients use capabilities to control actions, and Server independently authorizes every operation. Client-supplied role fields never grant access. See the OpenAPI specification for the full contract.

## Project configurations

Core Agent projects show AI models first in configuration details. Add system subscription models and third-party API models to one list, then edit, delete or set the default. Add and edit actions open a dialog with a segmented source selector. System AI needs only Provider and model selections and generates the name automatically. Fields have bordered groups, and the lone Configuration values tab is hidden when publication management is unavailable. After saving, Studio / CLI Web composers select only saved entries. Third-party models work independently of system AI sign-in; sharing excludes values by default, while complete backups contain model keys.

Authors can declare `allowThirdParty: false` on the model field in the source `configuration.json`. The editor then only offers system AI. Third-party saves and imports fail atomically, and publishing the model field retains this rule. Existing third-party entries display as unavailable and can be removed or replaced with system models. Execution also rejects custom endpoint overrides.

Projects can declare a single Subagent model selector with `control: "agent-model"`. Choose Follow main model or one entry from the same AI models list; removed selections remain visibly unavailable. See [Project configurations](/en/concepts/project-configuration#subagent-model-selection) for the declaration and Core binding.

### View, select, and save configurations

The configuration page opens with a profile list. Click a profile to view its fields and publication permissions, then use Back to list to return. The active profile has a highlighted row and an In use badge; other profiles offer a Use this configuration button. Viewing a profile preserves the execution selection. Switching disables duplicate actions, and failure keeps the previous selection and allows retrying. Unsaved values and permission rules must be saved or discarded before returning.

Edit fields directly and save changes together. Use the reset icon to restore a default or clear a field without a default; no separate enable checkbox is needed.

All three project types expose fields, named profiles and complete import/export. Studio and local CLI share local storage; Server values are per project and account. Studio Control can query and manage configurations even when the panel is closed. See [Project configurations](/en/concepts/project-configuration) for the JSON actions, version checks and execution snapshot rules.

File configuration fields upload personal attachments to Server storage. Field permissions and account isolation apply when saving their references.

### Publish configurations and restrict roles

Configuration authors use the separate **Publication and permissions** tab to select profiles, a default, value inclusion and field/JSON Pointer editing rules. Only maintainers, owners or system administrators may save official drafts. The recipient preview shows the filtered version; personal configuration imports never change official rules. Published source shares and downloads use that same immutable template and its attachment copies. See [Project configurations](/en/concepts/project-configuration).

After selecting a published version, users can read and edit permitted personal configurations even when the project has no draft. Draft publication checks are returned only when reading the draft.

Projects declaring `profilePolicy` filter configurations using actual project and inherited group roles. Guests see only guest base profiles such as Ask and may edit permitted values, while developers may use Build and manage personal profiles. Personal requests cannot change fixed modes, role labels, or minimum roles. Configuration responses, personal exports, and attachment reads share these checks. See [Project configurations](/en/concepts/project-configuration).

Personal configurations for v2 projects default to the latest published template. Source-draft access does not expose unpublished author fields or defaults. Maintainers, owners and system administrators retain official draft management. Role-controlled configurations must have a published template before developers use them.

## Manage databases and knowledge bases

The database catalog separates relational and knowledge resources with search and server pagination. Relational details show applied models, fields, fingerprints and paginated rows, with JSON insert/update/delete. Updates and deletes require a complete stable key and current row version. Knowledge details provide document lists, search, revision-aware editing and attachments. Resource pages manage account read/write grants and entry bindings. Navigation protects unsaved drafts; conflicts retain edits. Table DateTime values use ISO strings with a timezone and UTC semantics, and mapped enums use authored names. See the [Database API](/en/core-api/database) for encoding details.

Knowledge attachment contents use Server private file storage; PostgreSQL retains metadata, size and SHA-256. Backups must retain both the database and file storage directory. Legacy KV attachments are not imported, and there is no dual write or local fallback.

Studio and CLI Web deduplicate references by resource kind and UUID and open Server Web resource pages without putting account tokens in URLs. Visible KV editing and the local/remote KV switch have been removed. Account changes abort old requests and clear the catalog; changed bindings or grants invalidate old clients. Attachment preparation disables duplicate uploads, and closing the page cancels late results.

### Upload generated artifacts

Projects can include each source root's generated Node/Browser database assets and registered entries' static `build/<entryId>/` outputs under `dist/steamharness/`. Server verifies the inventory, definition and model fingerprints, and artifact SHA-256 without executing `steamharness.database.ts` or generated clients or installing dependencies. Other local `.steamharness` runtime data remains excluded. Regenerate changed models locally before upload. See [SteamHarness Database](/en/core-api/database).
