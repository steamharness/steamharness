# Version compatibility

Pin an exact SemVer in `devDependencies.steamharness` to record the version used for development and validation. Runtime compatibility compares `major.minor`.

## Determine compatibility

| Declaration | Meaning |
| --- | --- |
| `0.2.7`, `0.2.7-20260826001` | Examples of exact dependency declarations |
| `0.2.0`, `0.2.99`, `0.2.4-beta.1` | All belong to the `0.2.x` compatibility line |
| Different major or minor | Execution is rejected before loading user modules, with the required line reported |

Patch and prerelease identifiers do not order compatibility lines. Breaking API changes that require another line must increase minor rather than ship as a patch.

## Local execution and Server storage

1. Install the project's declared Core and CLI.
2. Studio resolves the CLI from that project and uses its Core for checks and execution.
3. The CLI verifies installed Core, its own exact binding, and the project declaration. Update mismatched dependencies to a validated combination.

CLI peer ranges stay within the same minor, such as `>=0.2.0 <0.3.0`. `run`, `json`, `structure`, and `resolve-params` all perform the compatibility check.

Server validates only static declarations and source snapshots. The local CLI still checks execution compatibility after download.

## Built-in project snapshots

Studio uses a pinned Developer Assistant snapshot. Studio Control belongs to the same aggregate and supplies permission-checked editor operations. They share identity, dependencies, and distribution.

Older indexes retain `components.core`, `components.cli`, and `minDesktopVersion` as historical release information. See [installation and startup](/en/guides/studio/installation) for running Studio from source.
