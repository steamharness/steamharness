# CLI and aggregate entries

Run the installed CLI from the aggregate root using Node.js 24. Install project dependencies first, then validate the root manifest and every registered entry. Child directories have no separate project identity.

Local runs may omit `steamharness.json.id` and do not require Server registration. Release builds require a valid project UUID in the authored manifest; local execution does not write an ID into source.

```sh
pnpm exec steamharness check .
pnpm exec steamharness check . --entry workflow
pnpm exec steamharness structure . --entry workflow
pnpm exec steamharness run . --entry workflow --entrypoint summarize -- --text example
pnpm exec steamharness json . --entry workflow --entrypoint summarize -- --text example
pnpm exec steamharness web . --entry agent
pnpm exec steamharness mcp . --entry workflow
```

## Entry selection

`--entry` selects the window entry. `run`, `json`, `structure`, `mcp` and `web` default to `defaultEntry`. `check` inspects all entries unless `--entry` selects one. `--entrypoint` selects an operation inside a Workflow. Keep the two identifiers distinct.

Entry IDs and paths follow the [reserved artifact name rules](/en/concepts/data-storage#artifacts-and-runtime-data), avoiding collisions with caches, reports, and Windows device names.

Arguments after `--` pass unchanged to the Workflow. `--locale zh-CN|en` selects host text without altering business parameters.

## Build and run a release

Build a release from the aggregate root, or prepare the latest release when starting an entry:

```sh
pnpm exec steamharness release . --json
pnpm exec steamharness run . --release --entry workflow --entrypoint summarize -- --text example
pnpm exec steamharness web . --release --entry agent
```

The release project is written to `dist/steamharness/release/project/`, with its archive under `dist/steamharness/release/`. The `--release` option on `run`, `json`, and `web` runs only entries included in the release configuration. A failed build reports an error and preserves the previous complete output.

When a project uses `file:` references to bundled Core and CLI tarballs, the CLI reads the versions from those tarballs. No separate `steamharnessRuntime` field is needed. If the bundled CLI still requires that field, update both packages before building a new release.

LLM Bots do not use project memory and do not need a memory switch to build a release. For Agent Bots, the memory default comes from the selected release entry and configuration definition, including `entry` and `configuration` under `release.entryOverrides`. Adding the switch preserves v2 configuration profiles.

Project declarations, configuration definitions, and extra JSON assets are minified to a single line. Field names, string content, and original number literals are preserved. Server configuration publication also minifies JSON before updating the file inventory.

The v2 `structure.json` format keeps project ID, entry ID, entry name, and type in plain text, with internal structure encoded as `brotli-base64`. The SDK, CLI, and Server share a decoder for inspection, execution, and static validation.

Use a matching host and rebuild older releases from source. Corrupt payloads and structures larger than 64 MiB after decompression are rejected. This encoding is not encryption; hosts can restore the structure.

In Studio, click **Run (Release Mode)** beside the Run button. Studio saves the project files, builds the release, and opens a new window rooted at the release run directory with the selected entry. That entry must be included in the release configuration.

Release windows start in the Steam layout and show project loading progress without passing through IDE mode or opening Assistant. The main project stays in the primary area. Restoring a tools tab for the same project does not make startup or retries use that tab.

The release window shows the aggregate project's logo and name in the upper left, stays in Steam mode, and omits Editor and Assistant from the tools area. Tools start collapsed when entering Steam mode or reopening a window. Click **Show Tools** in the upper right to expand the area with its saved tabs and width.

Source windows show the version declared in source. Opening a release project shows its installed version and checks for upgrades.

## CLI Web

Local hosts can use `--folder-context` to run a Bot that supports [folder context](/en/core-api/overview). This flag requires `--host-stdio`, `--entry` pointing to the default Bot, and a local directory passed by the host on standard input. It cannot be combined with `--release` or `--inspect`. Leave it out when starting CLI Web from a terminal.

See [Use CLI Web](/en/cli/web).

Ask a Bot, “What runtime am I using?” to check the Core, CLI and project versions. The [`runtime_info` tool](/en/core-api/agent/context#your-own-tools) distinguishes direct CLI runs, CLI Web, and Studio. Agents also report the working directory; [LLM Bots](/en/core-api/define-bot) omit local paths.

## Validation and output

`check` and `structure` statically inspect registered entries without executing user modules. Unsafe paths, duplicate entry IDs, invalid defaults, mismatched types and legacy declarations fail. `json` returns a run report with project and entry identity. Failed runs return a nonzero exit code. Cancellation propagates to the current execution and calls to other entries.

CLI Web and Studio can display inline images in run results. Click an image to enlarge it, or reopen the record to view it later. If an older page stays on progress text after a successful run, update the CLI, refresh the project page, and reopen the record to see the saved image without running the workflow again.

Use [workspace commands](/en/cli/server-workspace) for remote static project management. Server never executes project code.

Kanban cards in assistant replies preview their saved project, entry and configuration, keeping the owning host's entry prefix in resource URLs. Studio's `get_kanban_diagnostics` covers both open workspace boards and assistant cards, returning page instances, configuration identity and the latest 50 requests; `previews` identifies card sources. Use the current `instanceId` and `configurationId` to call page methods explicitly declared `readOnly: true` and verify actual state such as image readiness.

Closing or refreshing a card invalidates its old instance; missing live instances do not prove successful rendering. File bridge reads allow up to 120 seconds without an earlier transport timeout; reads exceeding that limit still require investigation of the file path.

When a Kanban board or embedded conversation fails, note the operation and error code in the alert. If it includes a diagnostic ID, use Studio's `get_kanban_diagnostics` to find that ID among recent requests for the board or card. Failed requests include a category, such as timeout, connection, or permission; file reads also list the sources they tried.

Search the CLI host log for the same ID to find the underlying exception. Read diagnostics before refreshing the board, which clears these records. A Workflow business rejection shows its user-facing reason; other host exceptions do not expose raw paths or credentials to the page.
