# CLI and aggregate entries

Invoke the installed CLI from the aggregate root. Use Node.js 24 and install dependencies with the declared package manager. The root manifest and registered entries must be valid. Child directories do not own independent SteamHarness project identities.

```sh
pnpm exec steamharness check .
pnpm exec steamharness check . --entry database
pnpm exec steamharness structure . --entry database
pnpm exec steamharness run . --entry database --entrypoint search -- --query example
pnpm exec steamharness json . --entry database --entrypoint search -- --query example
pnpm exec steamharness web . --entry agent
pnpm exec steamharness mcp . --entry database
```

## Entry selection

`--entry` selects the window entry. `run`, `json`, `structure`, `mcp` and `web` default to `defaultEntry`. `check` inspects all entries unless `--entry` selects one. `--entrypoint` selects an operation inside a Workflow. Keep the two identifiers distinct.

Entry IDs and paths follow the [reserved artifact name rules](/en/concepts/data-storage#artifacts-and-runtime-data), avoiding collisions with caches, reports, generated databases, and Windows device names.

Arguments after `--` pass unchanged to the Workflow. `--locale zh-CN|en` selects host text without altering business parameters.

## CLI Web

In the main Bot composer, type `@` to select **Skills**, **Files** or **Project entries**, or keep typing a name to search across them. Skills come from the current entry's configured directories. Files are searched from the project root, or Assistant's bound working directory. Git projects respect ignore rules; dependencies, build output, runtime data and `.env` configuration are excluded. Use ↑/↓ to select, Enter or Tab to insert, Esc to dismiss, and Shift+Enter for a new line. Inserted `@skill:…`, `@file:…` and `@entry:…` references are highlighted in the composer. File references display only the file name, with full paths on hover and automatic quoting for names containing spaces. Stored and sent messages retain full paths. References remain message text when restoring drafts, editing queued messages or resending. Referencing an entry neither switches windows nor runs it. Existing `/` commands remain available.

Core Agents use built-in/custom models from Settings in Studio by default or with `modelSource: "user-settings"`, hiding project AI models. Standalone `steamharness web` lacks model settings and automatically uses project models; Configure model opens project configuration with System AI and Third-party AI sources. An empty Studio catalogue still opens Settings. Explicit `modelSource: "project"` always uses project models.

When an execution worker unexpectedly exits under a live host, Core Agent entries automatically recover up to three times with the original tasks, child conversations and checkpoints. Local execution locks release when the old process exits. Explicit Server storage can wait up to 35 seconds for an old execution lease to expire. Recovery responds to cancellation and neither takes over another active owner nor replays committed writes. After a forced host exit, ordinary conversations recover using their original run identity; unfinished business work waits for explicit input. Host shutdown closes workers; workers that do not finish cleanup exit within five seconds to release conversation ownership. Failure, stop or timeout preserves and pauses queued input. Only a successful turn automatically starts the next queued message. You can explicitly resume the queue or send new input; successful new input then advances the retained queue in order.

When reopening a conversation or synchronizing history from another window, persisted Agent turn outcomes correct stale responding and recovery flags. Completed, failed and stopped replies stop counting elapsed time and are not executed again because of old flags. Unfinished turns continue through normal recovery. Each reply keeps its final duration after completion, including after refreshing or reopening history. Follow-ups are timed independently from when their execution starts. Subagent views use persisted execution timestamps when first opened or restored, including time spent running before the view opened and excluding queue time. Older history without reliable timing records is not backfilled from the current time.

In Studio, click local file links, inline code paths or plain absolute paths in Agent replies and plans to open the file in the editor. Relative paths, `file://` links and locations such as `src/main.ts:12:3` or `src/main.ts#L12C3` are supported. Relative paths resolve from the aggregate project root or Assistant's bound working directory. Web links open in the browser. Standalone CLI Web cannot open the local editor and prompts you to use Studio when opening a local path.

Exporting a conversation, message or workflow record in Studio opens the native save dialog, defaulting to the Downloads folder in your home directory. You can choose another location. After you confirm a location and the file is written successfully, a notification in the lower-right corner shows the saved path. Cancellation shows no success notification; save failures show an error. Standalone CLI Web uses browser downloads.

One root directory starts one aggregate host and initially displays only `defaultEntry`. Click the **Project windows** icon in the top toolbar to see compact entry cards with names, types, default/current markers and runtime states. Use the open icon on the right to open a new browser page in standalone CLI Web or a new native Studio tab. Every click creates another tab, including for the current entry. Tabs retain independent page state and drafts on the shared aggregate host. Closing one tab leaves the others open; closing the last Studio tab releases the host.

Each entry has an `/entries/<entryId>/` URL and independent controller. Its optional `projectCard` configures `icon`, `iconColor` and `iconBackgroundColor`, with `#RRGGBB` colors. Omitted properties use defaults for that entry type. The root `steamharness.json.projectCard` identifies the aggregate card; entry icons are independent. Declare the sole version in root `steamharness.json.version`; entries do not accept their own version.

Use the **Project information** icon in the upper-right corner to access Overview, Project configurations, Tools, Skills and Databases in one panel. Its width and height stay fixed, with sidebar navigation on wide screens and horizontally scrolling tabs on narrow screens. Content scrolls independently, and switching sections preserves configuration drafts and tool searches. Tool registrations and permissions update with the project state. Tools and skills are available for supported entries. The Skills page lists and counts actual guides for the selected entry, distinguishes project guides from Core built-in guides, and supports search. Select a guide to preview its complete `SKILL.md` or Markdown source inside the fixed panel. The return toolbar stays fixed while the document scrolls in its own area; returning preserves search and scroll position. Skills are read-only, without Enable or Auto-approve switches, and previewing does not execute instructions. Existing model setup shortcuts open Project configurations inside this panel.

Select **Project information → Databases** to view relational and knowledge resource references, status and sharing entries. Binding follows each resource type's rules; browsing opens the Server Web resource page without account tokens in the URL. Create resources, manage grants and edit data in Server Web or CLI management commands.

Entries declare `databases` and `knowledgeBases` aliases separately in `steamharness.json`. Server stores relational bindings by account, project, entry and alias. Root `config.json.knowledgeBases` stores knowledge alias-to-UUID mappings with `STEAMHARNESS_PROJECT_CONFIG` overrides. Entries may use multiple resources; binding grants no access. See [Project storage](/en/concepts/data-storage).

## Validation and output

`check` and `structure` statically inspect registered entries without executing user modules. Unsafe paths, duplicate IDs, invalid defaults, mismatched types and legacy declarations fail. `json` returns a run report with project and entry identity. Failed runs return a nonzero exit code. Cancellation propagates to the current execution and calls to other entries.

Use [workspace commands](/en/cli/server-workspace) for remote static project management. Server never executes project code.

Kanban cards in assistant replies preview their saved project, entry and configuration, keeping the owning host's entry prefix in resource URLs. Studio's `get_kanban_diagnostics` covers both open workspace boards and assistant cards, returning page instances, configuration identity and the latest 50 reads; `previews` identifies card sources. Use the current `instanceId` and `configurationId` to call page methods explicitly declared `readOnly: true` and verify actual state such as image readiness. Closing or refreshing a card invalidates its old instance; missing live instances do not prove successful rendering. File bridge reads allow up to 120 seconds without an earlier transport timeout; reads exceeding that limit still require investigation of the file path.

## User models and permissions

Studio can inject user permission snapshots and updates into CLI Web, using a capability handshake for older CLIs. Projects inherit only with explicit `permissionPolicy: "inherit"`; an omitted policy still defaults to `workspace`. Standalone CLI does not persist this preference in this release, and `inherit` uses `auto` without host injection. Active durable work keeps its startup snapshot; subsequent input adopts updates at a safe idle boundary. See [User settings and permission inheritance](/en/core-api/user-settings).

Quick menus bound to user models show model choices first and keep **Add model** available while loading or running work. Choices that cannot currently change remain disabled. With no available models, the control shows **Configure model** with setup guidance and opens model settings directly; adding a model restores the selection list. A model parameter named `inherit` is an ordinary model ID, not a permission inheritance marker; reset the model parameter to follow the user default.

Model and effort use separate Quick controls in the default Agent and assistant. Model choices group built-ins above custom models, with Add model fixed at the bottom. Custom project parameter groups remain supported.

CLI Web accepts host user model snapshots and updates. Bind a model parameter with `userSetting: { key: "agent.model", mode: "default" }` to open available choices before **Add model** opens Studio settings. Explicit choices become conversation overrides; resetting follows the user default. Entries may also use project model configuration APIs; standalone CLI does not persist Studio user models. Third-party keys are excluded from page state, ordinary history and exports, and durable sessions adopt changes after active work finishes. See [user settings](/en/core-api/user-settings#user-models-and-agents-without-connection-configuration).

## Forking conversations

The fork button below a response asks for confirmation, then shows creation and opening progress in a dialog. Success opens the branch automatically; failures display their reason. If creation succeeds but opening fails, the dialog identifies that result so you can open the saved branch from history. The branch contains history up to and including the selected response, excluding later messages. Creating a branch only changes saved conversation records: it does not call AI, rerun the project or resume old tasks, and works when System AI is unconfigured or unavailable. The original conversation is preserved. Model validation and execution begin when you send new input in the branch.

## Agent batches and pending user messages

The **Errors** filter in Studio Trace collects run, node and tool failures and model retry reasons. Existing diagnostics remain available after a successful retry and can be filtered by conversation and turn. Execution failures do not occupy the operation alert above the composer. Parameter validation, attachment and resource-opening errors remain in that alert; use **×** to hide them. Dismissing a parameter error does not bypass validation.

Durable Agent conversations show a **Subagents** entry beside “Responding…” with running, queued, failed and completed counts for the current conversation. Click to expand tasks, then expand an item to see its role, phase, progress, current activity, result and error. **Open child conversation** opens the corresponding independent conversation. Both anonymous delegations and named project roles are supported; tool calls, other conversations and independent forks are excluded from the counts. The entry updates from task snapshots, remains after the parent reply, and preserves expansion across subsequent replies. Offline snapshots are identified and child navigation stays disabled until reconnection. Studio and standalone CLI Web share this interface; Studio Tasks/Trace retains full task management.

Each subagent row shows elapsed time and token usage on the right, with status in its icon and expanded details. Timing starts at execution, excludes the admission queue and freezes when settled. Disconnection or interruption freezes the last snapshot; legacy records without reliable timing show “—”. **Bot usage** below the latest response includes all committed usage of the main conversation and its owned subagents and keeps updating during background work, including failed retries and spend before cancellation. Hiding a child does not reduce the total, and reopening does not add it again. Independent forks have separate totals; the answer's own turn usage remains separate. Disabling token-usage display in the project also hides these token statistics.

Work in the `needs_review` phase, or with a `MEDIA_RESULT_UNKNOWN` or `BODY_RESULT_UNKNOWN` outcome, shows **Awaiting verification** in its icon and details in a warning color, retaining its reason and unfinished progress. The child conversation shows the same task status and progress above its messages. A finished reply or a saved draft does not establish business completion. Verified work shows as completed, cancellation stays stopped, and independent forks do not inherit the source task banner. Offline status represents the last known snapshot.

Tasks shows roles, sources, phases, queued state and completed/target counts. Open child conversations, stop an item, retry failed work or stop a batch through Core control. Business queues and pending user messages are stored separately. Ordinary messages entered while busy remain in the host until a successful user turn finishes, then submit one at a time. Background reports never advance the user queue. Failure, cancellation and forced exit preserve and pause pending messages. Reopening unfinished business work does not rerun its batch automatically: explicit input first clears the old tree, and project recovery tools resume the batch with drafts and verified receipts intact.

With input queuing enabled, send consecutive messages without waiting for earlier delivery confirmations. New input after Stop submits directly; older queued messages wait for a successful turn before continuing. Clicking **Send now** or × immediately removes that pending row. Failed actions restore the original message with a retry control. Withdrawing local pending input while a new conversation is being created prevents it from being sent when creation finishes.

Composer **Stop** cancels the current conversation's entire execution tree, including background batches and subagents, while excluding independent forks. Background work keeps Stop available. Unexpected execution worker crashes first recover the existing tree under the current host. Queued input stays paused during recovery and successful replies remain successful. After automatic recovery is exhausted or the host itself is forcibly closed, explicit input first clears the old tree and adopts updated configuration at an idle boundary; project recovery tools can then resume business batches. Use `cancel scope=foreground` in Tasks/Trace when only foreground work should stop.

A fork is an independent new conversation with its own Server session, execution host, lease and configuration. Model, reasoning effort, Plan mode and tool permissions can be changed independently. Stopping, deleting or reopening the source does not stop or delete its branches. Managed attachments referenced in branch history are copied into the new conversation. Tasks, approvals, retries, usage and control receipts from the source execution are not imported. Legacy shared-host and SQLite branches are not migrated. Project-shared databases remain governed by project configuration and are not copied with a conversation. A source link remains below the title.

Fork and child navigation requires a matching request from the current page and conversation. Late, duplicate or unrelated receipts never switch conversations automatically. Subagent detail views remain part of their owning execution tree; user-created branches are managed as independent conversations.


## Database models and generation

`steamharness database` (short form `steamharness db`) provides `init`, `validate`, and `generate`. An optional project directory defaults to the current directory. Declare multiple aliases in `steamharness.database.ts` and models in `steamharness.schema`; generation requires no database connection. `workspace pack` generates and includes Node/Browser artifacts for the aggregate root and registered entries. Upload and download verify static inventories and hashes.

```sh
pnpm exec steamharness database init .
pnpm exec steamharness db validate .
pnpm exec steamharness database generate .
pnpm exec steamharness database generate . --entry billing
```

Directory arguments always select the aggregate project root. Without `--entry`, `validate` and `generate` process the root and all declared entry definitions, deduplicating source roots. `--entry <id>` selects that entry's source root. `init --entry <id>` creates definitions there without requiring a built entry. JSON results contain an `outputs` array with `sourceRoot` and `databases`; generation also returns `directory` and `cached`. Root definitions use `dist/steamharness/generated/database/`; child definitions use `dist/steamharness/entries/<encodeURIComponent(entry.root)>/generated/database/`. Kanban builds share the source root's parent directory with generated code: root entries default to `dist/steamharness/build/<entryId>/index.html`, and child entries use `dist/steamharness/entries/<encodeURIComponent(entry.root)>/build/<entryId>/index.html`. Explicit entries under `dist` must also use their own build directory; builders clean only that directory.

Resource and migration management also provides `create / list / inspect / retry / grant / revoke` and `migrate dev / deploy / status`. `migrate dev --draft` saves reviewable SQL, a model snapshot and checksums; `deploy` applies existing history only. `--database` selects a resource UUID and `--alias` a model declaration (default main). Management commands require a target Server account login; `--server` and `--token` override the target. See [SteamHarness Database](/en/core-api/database). Bind relational resources with `bind [directory] --database <id> [--entry <id>] [--alias main] [--mode read|write]`, list mappings with `bindings [directory] [--entry <id>]`, and remove them with `unbind [directory] [--entry <id>] [--alias main]`. Server stores bindings by account, project, entry and alias without modifying project files or granting permissions. Node entries query through `context.databases.connect(descriptor)`. Browser entries import generated browser descriptors and use the host table proxy through databases.connect, with rows/insert/update/delete delegates. Legacy KV and local KV APIs are removed.

Studio and CLI Web resource startup checks distinguish transport, login, access and binding failures. Temporary Server outages trigger a read-only check every 5 seconds, and recovery clears the temporary guidance. Checks never resubmit business operations.

Initial checks and successful results stay silent. Automatic retries and same-account verification retain the last completed result and page content until the check finishes; changing accounts or Servers clears the previous result and verifies the new identity. Failures include the HTTP status when available, recovery steps, and connection details showing the Server, project ID, and entry. Use Account / Server settings to check sign-in, Project information → Databases to check resource references, or Open Server project to inspect registration and access. Server 5xx responses require checking Server logs and registered entries. Use Create project only when starting a new application: it allocates a new ID and does not transfer existing data or access.

Background account checks keep configuration attachment uploads active. After the account changes or authentication is lost, the host rejects the previous account's upload result; select the file again under the current account.

Durable Agent command confirmation is independent of snapshot delivery. Confirmation timeouts and temporary connection failures retry automatically up to three times with the original request ID; recovery and late receipts reconcile the same input. Once project access recovers, recoverable runs continue with the original run ID. Stop cancels pending command recovery. Persistent failures retain their diagnostic and request identity for an explicit retry.

## Platform runtime history

Bot, Workflow and assistant history persist to host-local SQLite by default, including messages, runs, queues, drafts, parameters, usage and Agent checkpoints. Reopening restores committed history without a Server login or connection for storage. Replies stream immediately while host history writes are coalesced, without waiting for cloud uploads. System AI and business resources retain separate authorization. Local file locks coordinate windows and release on process exit. Select cloud storage explicitly, or use `copyRuntimePersistence` to back up an idle session to an empty destination in the background. Existing cloud and legacy local records are preserved without automatic migration or overwrite. Back up attachments and workspace files separately. See [runtime storage](/en/core-api/runtime-storage).

## Knowledge and table management

`steamharness knowledge` provides `create / list / grants / grant / revoke / bind / unbind / bindings / operation`. Bind with `--knowledge-base <UUID>`, `--alias <alias>` and `--entry <entry>`; alias defaults to main. `list --page 2 --page-size 20 --search Docs` paginates and filters on Server. `operation <UUID> knowledge.listDocuments < input.json` reads JSON from stdin without replaying mutations. Attachment contents allow 50 MiB.

`steamharness database data <UUID> < request.json` manages applied models with `models / rows / insert / update / delete`. Read schemaHash from models and send it on later requests. Updates and deletes also require the current rowVersion and complete stable key. Stdin is limited to 4 MiB. Encode BigInt and Decimal as decimal strings, DateTime as ISO with a timezone and Bytes as Base64. Dates use UTC, enums use authored names, and omitted lists without defaults become empty arrays. `database list` accepts the same pagination options. See [Knowledge API](/en/core-api/knowledge-documents) and [Database API](/en/core-api/database).

Kanban can invoke registered Workflows and subscribe to native Conversations through the aggregate host. See [Kanban](/en/concepts/kanban) and [Bot entry control](/en/concepts/database-and-conversation#local-conversation-entry-control). Each entry reuses its native controller, execution owner, and queue. Studio shares this host for the same aggregate project.

## Project release mode

`steamharness release . --json` writes a runnable distribution to `dist/release/project/` and a versioned archive beside it. Project UUID, version, entries, parameters, tools and configuration definitions remain readable. Business JavaScript is bundled and minified with local identifiers renamed; TypeScript sources and source maps are excluded.

```sh
pnpm exec steamharness release .
pnpm exec steamharness web . --release
pnpm exec steamharness json . --release --entry main
pnpm exec steamharness workspace pack example --path . --mode release
```

An optional `release` object in the aggregate `steamharness.json` selects the distribution:

```json
{
  "release": {
    "entries": ["agent", "database", "board"],
    "defaultEntry": "agent",
    "entryOverrides": {
      "agent": { "entry": "index.release.ts", "configuration": "configuration.release.json", "profiles": ["ask"] }
    },
    "build": ["corepack", "pnpm", "run", "build"],
    "files": ["README.md", "LICENSE"],
    "externals": []
  }
}
```

All entries are included by default. Override modules, configurations and `assets` are relative to the original entry root; `files` are relative to the aggregate root and support globs. Without `build`, the package's build script is used. Kanban requires a build step. Dependencies are bundled, while the SDK and Node built-ins are provided by the host. Explicit `externals` are recorded at their installed exact versions. Inclusion rules cannot override credential, source, test or runtime-data exclusions.

Entry selection must account for calls between entries. `profiles` restricts configuration only. To remove executable capabilities, provide a release-specific module and separate its dependencies from excluded implementations.

The `--release` option on run commands checks input fingerprints, rebuilds when necessary and runs an immutable build snapshot. Development and release sessions, configurations and checkpoints use separate namespaces in application/user data directories. They retain the same project UUID and Server resource bindings. Deleting `dist/` does not delete runtime data.

Studio provides **Run (Release Mode)** beside the normal run action, with cancellable build progress. Source projects display their authored version only. Downloaded or imported release projects check for upgrades and open in Steam mode with the IDE switch hidden. A release installation cannot be replaced by a source version.

Packing and uploading accept `--mode auto|source|release`, defaulting to `auto`. A release configuration or existing release output causes the latest distribution to be prepared and uploaded. Build failures stop the upload without falling back to source. `source` explicitly uploads source; `release` forces a release build. Release uploads use their validated inventory instead of inheriting source `.steamharnessignore` rules. Server configuration publication respects the release's profile and field limits.

`steamharness.release.json` declares the format version, build identity and file hashes. Hosts validate it when inspecting, running or downloading a release. Older hosts must upgrade to support this format. The command generates project artifacts; it does not publish npm packages or deploy services.
