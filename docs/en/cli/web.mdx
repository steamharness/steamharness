# Use CLI Web

Open local projects in a browser, switch entries, and inspect project information.

```sh
pnpm exec steamharness web .
```

## CLI Web

During a Bot reply, click **Send now** beside a queued message to move it below the current reply immediately. The Bot stops the current reply and starts a new one below the message. Any output already shown stays in the conversation, and other messages remain queued.

If sending fails, the message returns to the queue with an error and a **Retry** action. Pressing Enter with no text, attachments, or path references neither sends a message nor stops a task.

Click **Stop** to show stopping progress immediately in the reply and task plan. Displayed content and the composer draft are preserved, and the input queue pauses. You can send a new message once execution ends. Stopping a child conversation leaves the parent's other work running.

Connected pages send Stop directly. If disconnected, the page restores the connection before trying to stop. Failed requests show an error and can be retried.

In the main Bot composer, type `@` to select **Skills**, **Files** or **Project entries**, or keep typing a name to search across them. Skills come from the current entry's configured directories. Files are searched from the project root, or Assistant's bound working directory. Git projects respect ignore rules; dependencies, build output, runtime data and `.env` configuration are excluded.

Use ↑/↓ to select, Enter or Tab to insert, Esc to dismiss, and Shift+Enter for a new line. Inserted `@skill:…`, `@file:…` and `@entry:…` references are highlighted in the composer. File references display only the file name, with full paths on hover and automatic quoting for names containing spaces. Stored and sent messages retain full paths. References remain message text when restoring drafts, editing queued messages or resending.

Referencing an entry neither switches windows nor runs it. Existing `/` commands remain available.

When Studio desktop and the Bot run on the same machine, choosing, dropping, or pasting a disk file references its original path without copying it. If Studio cannot get the path, choose the file again using the attachment picker in the composer.

In a browser, choose a file or folder with the attachment picker, or drag it into the composer. Uploads go into `.steamharness/conversation-uploads/` inside the project working directory. Assistant uses its bound working directory. Uploads keep the folder structure intact and are labeled **Uploaded copy**. The Bot gets the copy's path on the execution host, not the client's original path. Deleting the conversation does not remove these copies.

Each import can contain up to 50 MiB. If the browser provides a path without the contents, select the file or folder again to upload it. For larger files, include a path the Bot can access in your message. Supported inline images still send as images.

File cards show the file name, format, and size when available. In desktop Studio, select a card to preview supported formats such as XLSX, PDF, and DOCX, or to reveal an unsupported file in your system file manager. In standalone CLI Web, select a file or folder card to see its details.

Core Agents use built-in/custom models from Settings in Studio by default or with `modelSource: "user-settings"`, hiding project AI models. Standalone `steamharness web` lacks model settings and automatically uses project models; Configure model opens project configuration with System AI and Third-party AI sources. An empty Studio catalogue still opens Settings. Explicit `modelSource: "project"` always uses project models.

When an execution worker unexpectedly exits under a live host, Core Agent entries automatically recover up to three times with the original tasks, child conversations and checkpoints. Local execution locks release when the old process exits. Explicit Server storage can wait up to 35 seconds for an old execution lease to expire. Recovery responds to cancellation and neither takes over another active owner nor replays committed writes.

After a forced host exit, ordinary conversations recover using their original run identity; unfinished business work waits for explicit input. Host shutdown closes workers; workers that do not finish cleanup exit within five seconds to release conversation ownership. Failure, stop or timeout preserves and pauses queued input. Only a successful turn automatically starts the next queued message.

You can explicitly resume the queue or send new input; successful new input then advances the retained queue in order.

If the first model connection or tool initialization fails, an idle conversation still accepts **Retry**, a new message, or an explicit queue continuation. Retry preserves the composer draft; failure alone never resends old input. `recovery.startup: "manual"` requires an explicit action for unfinished execution restored after reopening the host, without blocking new sends after a failure.

When reopening a conversation or synchronizing history from another window, persisted Agent turn outcomes correct stale responding and recovery flags. Completed, failed and stopped replies stop counting elapsed time and are not executed again because of old flags. Unfinished turns continue through normal recovery. Each reply keeps its final duration after completion, including after refreshing or reopening history. Follow-ups are timed independently from when their execution starts.

Subagent views use persisted execution timestamps when first opened or restored, including time spent running before the view opened and excluding queue time. Older history without reliable timing records is not backfilled from the current time.

When an Agent calls `sleep`, the activity row shows its expected end time. Expand it to inspect the waiting result; completion shows the actual end time. Times use the browser's local timezone and remain available in history. Resuming a wait retains its original deadline.

When all subagents have ended and their queue is empty, an internal status input resumes the parent and can end sleep early. It creates no user bubble or pending input row, including after history replay. Normal assistant continuations remain visible. The notification does not independently unpause the user queue.

In Studio, click local file links, inline code paths or plain absolute paths in Agent replies and plans to open the file in the editor. Relative paths, `file://` links and locations such as `src/main.ts:12:3` or `src/main.ts#L12C3` are supported. Relative paths resolve from the aggregate project root or Assistant's bound working directory. Web links open in the browser. Standalone CLI Web cannot open the local editor and prompts you to use Studio when opening a local path.

Exporting a conversation, message or workflow record in Studio opens the native save dialog, defaulting to the Downloads folder in your home directory. You can choose another location. After you confirm a location and the file is written successfully, a notification in the lower-right corner shows the saved path. Cancellation shows no success notification; save failures show an error. Standalone CLI Web uses browser downloads.

One root directory starts one aggregate host and initially displays only `defaultEntry`. Click the **Project windows** icon in the top toolbar to see compact entry cards with names, types, default/current markers and runtime states. Use the open icon on the right to open a new browser page in standalone CLI Web or a new native Studio tab. Every click creates another tab, including for the current entry. Tabs retain independent page state and drafts on the shared aggregate host. Closing one tab leaves the others open; closing the last Studio tab releases the host.

Each entry has an `/entries/<entryId>/` URL and independent controller. Its optional `projectCard` configures `icon`, `iconColor` and `iconBackgroundColor`, with `#RRGGBB` colors. Omitted properties use defaults for that entry type. The root `steamharness.json.projectCard` identifies the aggregate card; entry icons are independent. Declare the sole version in root `steamharness.json.version`; entries do not accept their own version.

Use the **Project information** icon in the upper-right corner to access Overview, Project configurations, Tools and Skills in one panel. Its width and height stay fixed, with sidebar navigation on wide screens and horizontally scrolling tabs on narrow screens. Content scrolls independently, and switching sections preserves configuration drafts and tool searches. Tool registrations and permissions update with the project state. Tools and skills are available for supported entries.

**Overview** uses the same layout as the Studio project library. It shows the version, project location, and default entry. To open another entry, use **Project windows** in the toolbar. In Studio, the overview also shows the current project's local usage. For supported Bots, **Bot management** appears in the overview; closing the artifact, memory, or credential dialog leaves the project details open.

The Skills page lists and counts actual guides for the selected entry, distinguishes project guides from Core built-in guides, and supports search. Select a guide to preview its complete `SKILL.md` or Markdown source inside the fixed panel. The return toolbar stays fixed while the document scrolls in its own area; returning preserves search and scroll position. Skills are read-only, without Enable or Auto-approve switches, and previewing does not execute instructions.

Existing model setup shortcuts open Project configurations inside this panel.

## When the Server connection fails

Workflow, Bot, and Kanban entries run locally without Server sign-in, cloud registration, or project ID validation. Source manifests may omit `id`; a valid project UUID is required when building a release.

Run pages do not show advance Server or AI connection checks, and offline services do not hide the composer, execution form, or board. If an entry actually calls a model or another online service and that call fails, the error belongs to that run and remains available in its result or logs.

## Local resource previews

Project, Kanban, and file cards can be previewed within the current aggregate. Kanban uses a restricted page, and file cards use paths relative to the project. The host cancels unfinished reads when a card closes or its access identity changes.

In Studio, a card’s **Open beside** button uses an existing editor group beside the conversation, creating a split when needed. Later cards update the same preview tab without opening a separate native window.

## Workflow output pages

Workflow results display 100 output items per page. Studio uses the same page. A running view follows the latest page until you select **Previous**. New output then leaves the selected page in place; select **Latest** to resume following.

Local runs save every output incrementally and load only the selected page, with images loaded on demand. Pages remain available after stopping, cancellation, or reopening a run. A failed read keeps the displayed content and offers a retry. Export includes the complete output; deleting the run removes its history and associated attachments.

## Following output and activity records

Workflow results follow the bottom of the latest page, including layout growth after images load. Scrolling up, selecting text, or opening details pauses following. Choose **Scroll to latest**, or scroll back to the bottom, to resume. Older pages preserve their reading position; the pagination control's **Latest** restores the newest page and following.

Business output using `activity-record` appears as separate cards with a title, time, target fields, summary, and image. In wide views, text appears on the left and the image on the right; narrow views stack them. Select an image to open the full preview. Complete text remains expandable. Adding images preserves earlier cards and their expanded text.

## Opt into platform features

Platform credentials are not read by default. Use `--online project` for protected project configuration, or `--online ai` for System AI. Each option requires a Server connection and its own login. Repeat the flag to enable both.

Hosts embedding CLI Web can read `restrictedConfigurationEntries` in the `--json` startup response to identify entries with role restrictions, then supply a project account through the host protocol. The list grants no permissions; visible configurations still depend on the current project role verified by Server.

When CLI Web starts with `--host-stdio`, `studioPreviewProtocolVersion: 1` in the `ready` response indicates support for Studio Web preview URLs. The field does not change how standalone CLI Web is accessed.
