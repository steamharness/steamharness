# Scheduled Workflow Runs

A schedule invokes a Workflow operation according to time rules, creating an independent run for each fire. Bot and Kanban cannot be scheduled targets. The selected operation does not first execute the default operation.

In Studio desktop, open **Project library → Project details → Workflow schedules**. Schedules are available for trusted local source projects. If the project contains several Workflow entries, choose the entry first, then select the operation in the schedule panel.

1. Select **New schedule**, then choose the time zone and rule. You can also start from one of the project's **Suggested schedules**.
2. Select **Preview next five** to check the times. Saving validates the operation and its parameters without running the project.
3. Select **Enable schedule** and confirm the folder, entry, version, and time zone. To test it once, select **Run now** without enabling the schedule.

The project needs a version of the SteamHarness CLI that supports schedules. When Studio shows an upgrade prompt, update that project's runtime. Studio does not change project dependencies automatically.

## Trigger rules

Schedules use an IANA time zone and support two trigger types:

- `window-interval`: choose weekdays, one or more time windows, and an interval in minutes. A window includes both endpoints, so `09:30-11:30 / every 5 minutes` fires at both `09:30` and `11:30`.
- `cron`: a five-field Cron expression evaluated in the schedule time zone. Cron seconds are not supported.

```ts
type ScheduleTrigger =
  | {
      kind: "window-interval";
      weekdays: number[]; // 1-7, Monday through Sunday
      windows: Array<{ start: string; end: string }>;
      intervalMinutes: number;
    }
  | {
      kind: "cron";
      expression: string;
    };
```

Schedules accept only the operation's declared static parameters. File inputs and date placeholders are not supported. For a value such as “today,” read the current time in the business time zone inside the Workflow. Do not put credentials in schedule parameters.

## Recommended schedules

A Workflow can provide recommendations through `steamharness.json.entries[].schedulePresets`:

```json
{
  "type": "workflow",
  "name": "Scheduled workflow",
  "entry": "index.ts",
  "schedulePresets": [
    {
      "id": "hourly",
      "title": "Hourly sync",
      "entrypointId": "sync",
      "timezone": "Asia/Shanghai",
      "trigger": {
        "kind": "cron",
        "expression": "0 * * * *"
      },
      "paramValues": {}
    }
  ]
}
```

A preset ID must match `/^[a-z][a-z0-9_-]{0,63}$/`, be unique within the project, and reference a declared Workflow entrypoint. A preset is only a recommendation: a local scheduling host may display and confirm it. Importing or publishing a project never enables a schedule automatically.

## Scheduling Boundary

Studio fires schedules only while it is running locally and the device is awake. Occurrences missed while Studio was closed or the device was asleep are recorded as **Missed**, not run later. Opening multiple Studio windows does not duplicate a trigger. If the folder, source version, or trust status changes, affected triggers are skipped with a reason in history.

Server does not execute schedules. Uploading a project does not create a schedule, and the standalone CLI does not start a background scheduler.

## Overlap, waiting, and history

If the previous run is unfinished, the trigger is recorded as `skipped_overlap`. It is not queued or retried. A run waiting for approval or input still counts as unfinished. Select **Trigger history → Open original run** to respond in that run.

Every scheduled run records the following information in its run history, summary, and report:

```ts
{
  source: "schedule";
  scheduleId: string;
  scheduleName: string;
  fireId: string;
  scheduledFor: string;
  triggerKind: "window-interval" | "cron";
}
```

The Schedule page shows the enabled state, rule, time zone, version, entrypoint, next fire, recent results, and skip reason. It also lets you trigger the schedule once and inspect its fire history. Manual triggers still follow the same overlap rules.

You can pause a schedule while it is queued, running, or waiting for input, but you cannot edit or delete it. Pausing does not cancel a run that has already started. After editing a schedule, save and enable it again.

## Kanban integration

Schedules and trigger history are scoped to the local source folder, `projectId`, and `entryId`. `entrypointId` identifies the operation.
