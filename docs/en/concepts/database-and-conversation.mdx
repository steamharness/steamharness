# Databases and conversations

Business models, knowledge bases, and runtime records have independent resources and lifecycles. Creating a project or conversation never provisions a business database automatically.

## Business tables

Define aliases in `steamharness.database.ts` and models in `steamharness.schema`. List the aliases in the entry's `databases`. Server stores bindings by account, project, entry, and alias; project configuration contains no business database IDs or credentials.

```ts
import { main } from "./.steamharness/generated/database/node/index.js";
const db = await context.databases.connect(main);
const users = await db.user.findMany({ orderBy: { id: "asc" } });
```

Each resource owns an independent PostgreSQL database. Projects A and B can both define `User` while binding different resources to isolate schemas and rows. Sharing requires explicitly binding the same UUID. Transactions apply to one client and do not span databases. See [Database API](/en/core-api/database).

## Aggregate calls

```ts
const result = await context.entries.get("jobs")
  .runEntrypoint("refresh", ["--limit", "10"]);
```

Only registered Workflow entries are callable. The host preserves the actor, cancellation, and tool restrictions and checks the target configuration and bindings again. Calling an entry does not grant direct access to its database.

## Knowledge and attachments

Use `context.knowledgeBases.get("docs")` for documents and its `files` member for attachments. Knowledge resources have separate account grants and entry bindings without requiring a project schema. Private file storage holds bytes; relational tables hold metadata and versions. Business rows store references. See [Knowledge API](/en/core-api/knowledge-documents).

## Conversation and runtime storage

Conversations, messages, input queues, drafts, runs, usage and Agent checkpoints persist to host-local SQLite by default, isolated by project, entry and conversationId. Runtime history needs no business database grant and creates no remote database per session.

`context.conversation.getValue/setValue/setTitle/appendMessage` addresses the current conversation independently of business models. Configuration changes apply to the next execution; approval recovery must match the current project and entry.

Local persistent history requires no platform login or network connection; system AI and business resources retain their own authorization. Trusted hosts can explicitly select Server storage or use `copyRuntimePersistence` to copy idle sessions to an empty cloud destination in the background. This is an on-demand snapshot backup rather than continuous synchronization. Back up attachments and workspace files separately. Existing cloud and legacy local records are preserved without automatic reads, migration or dual writes; KV and PersistentValue remain removed. See [runtime storage](/en/core-api/runtime-storage).
