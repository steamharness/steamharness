# Independent database spaces

A database is an independent resource of a local or server host. One `spaceId` contains KV, knowledge documents, indexes, attachments and revisions. Multiple projects and entries may receive access. Deleting a project does not delete its spaces.

## Record database references

The aggregate root `config.json` stores deployment configuration. `databases` maps each unique alias to an approved database ID and contains no `entries`. Each `steamharness.json` entry lists the aliases it uses in a `databases` string array. The host manages permissions and credentials. Package entries accept alias strings only; old `{alias, databaseId}` objects and `host`, `permissions`, and `bindingRef` declarations are rejected.

```json
{
  "version": 1,
  "databases": {
    "data": "00000000-0000-4000-8000-000000000001",
    "archive": "00000000-0000-4000-8000-000000000002"
  }
}
```

Each entry references its required aliases in `steamharness.json`:

`steamharness.json`

```json
{
  "defaultEntry": "agent",
  "entries": [
    {
      "entryId": "agent",
      "root": "agent"
    },
    {
      "entryId": "database",
      "root": "database"
    }
  ],
  "id": "00000000-0000-4000-8000-000000000001",
  "name": "Example",
  "version": "1.0.0"
}
```

`agent/steamharness.json`

```json
{
  "type": "conversation",
  "name": "Agent",
  "entry": "index.ts",
  "databases": [
    "data",
    "archive"
  ]
}
```

`database/steamharness.json`

```json
{
  "type": "workflow",
  "name": "Database",
  "entry": "index.ts",
  "databases": [
    "data"
  ]
}
```

Replace example UUIDs with IDs approved by your host. Use one alias for each database, share it between entries, and associate multiple databases with an entry when needed. Application code uses `context.databases.get("data")`. To migrate every consumer, change `databases.data` once in `config.json`; subsequent executions resolve the new ID.

The `STEAMHARNESS_PROJECT_CONFIG` environment variable accepts a JSON object, such as `{"databases":{"data":"00000000-0000-4000-8000-000000000003"}}`. It overrides database IDs by alias, taking precedence over the file. A complete configuration can also be provided without a file. Unknown aliases, invalid UUIDs, and duplicate database IDs fail explicitly. Configuration does not execute project code or automatically load `.env`. Inject the variable when starting the host. Uploads, archives, and Store distributions preserve authored `config.json` values without writing the machine's environment overrides into source.

Host grants independently control `kv.read/write` and `knowledge.read/write`, using `{"mode":"none"}`, `{"mode":"all"}` or `{"mode":"prefixes","prefixes":["public:"]}`. KV listing applies the granted key range before pagination and counting. Client-supplied key prefixes may only narrow that range.

## Request and approval

1. Open **Databases** in the Studio sidebar or Steam tools and use the plus icon to request access. Server Web provides a request action in its database directory and a **Requests and permissions** page. CLI `databases` commands continue to support requests and reviews.
2. Select the local or server host, consuming project and entry, alias, new or existing database, and read/write scopes. A submitted request is `pending`; no space is created and data access remains unavailable.
3. The local host user reviews local requests. A Server system administrator approves new spaces, with the applicant becoming owner. The owner or a system administrator reviews shared access.
4. A reviewer may reject with a reason or narrow permissions before approval. Approval returns a `databaseId` and creates a host grant for the project and entry. No manifest reference is required before requesting access.
5. In CLI Web, open **Project information → Databases**, select the link icon and enter the alias and approved ID. Saving updates root `config.json` and adds the alias to the entry's owning `steamharness.json`; it does not create a database or grant access. CLI Web displays the name, ID, connection status, host and sharing entries. Requests, reviews and grant maintenance belong to host interfaces or CLI commands.

CLI Web and Studio share a user-level SQLite registry, with data directories separated by `spaceId`. Server persists its catalog and data in PostgreSQL. Project membership still limits the caller; database grants cannot elevate their role.

## Browse data

The Studio directory defaults to **Used by this project**, with local, server and all filters and name, ID or alias search. A database shared by multiple entries appears once with its consuming entries. Open a database, KV or knowledge child in an independent editor tab using the same paginated list and detail editor as the bottom resources panel. Opening the same target again reveals its tab. Host management can inspect retained local data; navigation from a project entry still enforces that entry grant.

Open project data tabs validate the alias against the database ID and host they opened. After migrating an ID through `config.json` or an environment override, close the old tab and reopen the database. Drafts from old tabs cannot write into the replacement database. Account changes cancel host requests and reviews that have not been submitted.

Server Web uses a directory and database tabs, with server pagination, project filtering, search, KV list and detail editing, knowledge, attachments and a separate requests and permissions page. It manages server databases and does not read local SQLite.

CLI Web's browse icon opens the corresponding Studio data tab. A standalone Web session reports that data preview is unavailable; use Studio or Server Web to browse.

## Use and share

```ts
const database = context.databases.get("data");
await database.transaction(async db => {
  await db.kv.setValue("settings:theme", "dark");
  await db.knowledge.createDocument({
    id: "guide", title: "Guide", markdown: "# Guide\nShared content",
  });
});
const theme = await database.kv.getValue("settings:theme");
const document = await database.knowledge.getDocument("guide");
```

Project and entry IDs authorize access and record its source; the space addresses data. Ordinary KV cannot read knowledge-reserved keys. Attachments require knowledge permissions. Every operation, transaction, CAS, lock and revision subscription rechecks authorization.

Two projects with approved bindings to the same space share keys, knowledge documents and attachments. Conversation KV remains isolated by project, entry and conversation identity. Knowledge indexes commit together with document mutations.

## Unavailable references

Unknown IDs and unavailable or revoked grants expose errors and host management actions. Other entries remain manageable and runnable. Uploads, archives and Store distributions preserve alias-to-ID references. A reference carries no credentials or permissions; the host always validates the caller, project and entry.
