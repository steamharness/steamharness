# Project storage

SteamHarness manages business models, knowledge content and runtime history separately. Persistent access is authorized by Server. Server and PostgreSQL may run locally: service connectivity is required, internet access is not.

| Data | Storage and isolation | Project API |
| --- | --- | --- |
| Custom business models | Independent PostgreSQL database and roles for each explicitly created resource | `context.databases.connect(descriptor)` |
| Knowledge documents, chunks, indexes and attachment metadata | Shared platform tables isolated by knowledge UUID and account grants | `context.knowledgeBases.get(alias)` |
| Conversations, messages, runs, queues, usage and Agent state | Shared platform tables isolated by account and runtime space | Host runtime storage |
| Knowledge attachment contents | Private Server file storage; SQL retains metadata and checksums | `knowledge.files` |

Creating a project or conversation does not create a physical database. Projects A and B can request separate resources and define different `User` tables. Sharing requires explicit binding to the same resource and authorization. Knowledge bases do not require a project-defined schema.

## Business databases

Declare aliases in `steamharness.database.ts` and models in `database/<alias>/steamharness.schema`. CLI generates typed Node/Browser descriptors. Use `steamharness database` for creation, grants, migrations and binding. Relational bindings are stored on Server by account, project, entry and alias, independently of legacy `config.databases`. Connecting does not create or migrate resources.

```ts
import { main } from "./.steamharness/generated/database/node/index.js";
const db = await context.databases.connect(main);
await db.user.create({ data: { id: "alice", name: "Alice" } });
```

See [SteamHarness Database](/en/core-api/database).

## Knowledge declarations

```sh
steamharness knowledge create "Docs"
steamharness knowledge bind . --entry main --alias docs --knowledge-base <UUID>
```

An entry declares `"knowledgeBases": ["docs"]` in `steamharness.json`. Root `config.json` stores deployment IDs:

```json
{
  "version": 1,
  "knowledgeBases": {
    "docs": "00000000-0000-4000-8000-000000000001"
  }
}
```

Replace the example UUID with the created resource ID. Entries may share an alias, and an entry may declare multiple knowledge bases. `STEAMHARNESS_PROJECT_CONFIG` accepts JSON such as `{"knowledgeBases":{"docs":"00000000-0000-4000-8000-000000000002"}}` to override IDs by alias. It does not load `.env`; distribution retains the original file without writing environment values into source. Missing or duplicate aliases and invalid IDs fail explicitly.

```ts
const knowledge = context.knowledgeBases.get("docs");
const doc = await knowledge.createDocument({ title: "Guide", markdown: "# Guide" });
await knowledge.editDocument({ id: doc.id, markdown: "# Updated", expectedRevision: doc.revision });
```

Server checks account grants and consumer bindings. Registered projects additionally require membership capabilities and matching entry declarations. After changing an ID, establish a matching Server binding and reopen the entry. Old clients cannot write a draft to a replacement resource. Grant changes and revocation invalidate clients too. `knowledge unbind` removes the Server binding while retaining the declaration for later rebinding. See [Knowledge API](/en/core-api/knowledge-documents).

## Management

Server Web offers relational and knowledge catalogs with server pagination, search and resource creation. Resource pages manage account grants and project entry bindings. Relational pages show applied models, fingerprints and table data; knowledge pages manage documents and attachments. Row mutations require a complete stable key and current row version. Conflicts retain drafts; navigation protects unsaved edits.

Studio's database view and CLI Web's project database panel show resource references and open the corresponding Server Web page without putting account tokens in links. These interfaces no longer expose KV editing or a local/remote KV switch. Legacy KV runtime and local storage APIs are removed without compatibility or automatic migration.

## Persistent history and failures

Platform runtime storage owns history independently of business and knowledge resource grants and lifecycles. Deleting a project does not automatically delete independent resources. Disconnection, revocation and storage failures fail explicitly without switching to local KV, JSON or SQLite history or clearing valid sign-in. See [runtime storage](/en/core-api/runtime-storage).
