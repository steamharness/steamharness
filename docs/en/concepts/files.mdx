# File Input

steamharness supports file input through executor params. Local clients save attachments first, then workflows read their contents through file references.

## file param

```ts
params: [
  {
    name: "images",
    flag: "--images",
    type: "file",
    multiple: true,
    accept: ["image/png", "image/jpeg", "image/webp"],
    format: "json",
    required: false,
    description: "Image attachment.",
  },
]
```

The value of the file param is serialized as a JSON string to `createInput`.

Images and videos share `type: "file"`. Set `accept` to the supported formats, for example
`accept: ["image/png", "image/jpeg", "video/mp4", "video/quicktime"]`, and declare the same
restrictions in `createFileInputNode`. CLI Web shows the corresponding upload
action, image thumbnails, and native video previews with download and removal actions. Video
references keep `kind: "file"` and are identified by `mimeType`; `toLLMImagePart()` remains image-only.

Core and Server infer MIME types for MP4, M4V, MOV, AVI, MKV, WebM, OGV, and MPG/MPEG.
An explicit `audio/webm` MIME remains audio. Restrict `accept` to formats supported by the model;
MiniMax-M3 accepts MP4, MOV, AVI, and MKV. A supported upload format may contain codecs that the
browser cannot play. CLI Web limits local uploads to 50 MiB per file; Server uses its managed file size limit.

Audio input uses `type: "file", control: "audio"`. The shared workspace supports recording, preview, re-recording, and choosing an existing audio file; recordings are encoded as mono 16 kHz PCM WAV and use the same file reference protocol. Set `audio: { maxDurationSeconds, maxBytes }` for limits. MiniMax speech recognition accepts one audio file up to 500 seconds and 50 MiB.

Browser recording requires a secure context, normally HTTPS or localhost. For a cross-origin iframe,
the host must grant `microphone` with `Permissions-Policy: microphone=(self "<embed-origin>")` and
set `allow="microphone"` on the iframe. Permission or device failures remain visible with a retry
action. Release tracks and temporary objects when switching projects or unmounting the control.

## FileInputNode

```ts
const imageInputNode = workflow.createFileInputNode({
  name: "images",
  accept: ["image/png", "image/jpeg", "image/webp"],
  multiple: true,
});

const images = await workflow.runNode(imageInputNode, input.images, context);
const imageParts = await Promise.all(images.map((file) => file.toLLMImagePart()));
```

`createFileInputNode` will resolve the reference through `context.files` and return `ResolvedFile[]`.

## ResolvedFile

Parsed file support:

```ts
file.readBuffer()
file.readBase64()
file.readDataUrl()
file.toLLMImagePart()
file.toJSON()
```

`toLLMImagePart()` only accepts image files; non-images throw an input validation error.

`context.knowledgeBases.get("docs").files.readFile(id)` reads a database attachment as a content snapshot. Calls such as `readBuffer()` and `readBase64()` on that handle reuse the downloaded content while checking the current database binding and read grant each time. Revoking or narrowing the grant also prevents reads through retained handles.

## Runtime build file

workflow When generating screenshots, exports, or other files while running, use
`context.files.createFile(...)`：

```ts
const file = await context.files?.createFile?.({
  name: "frame.png",
  mimeType: "image/png",
  buffer,
  kind: "image",
});
```

An explicit Server connection provides managed file storage. Returned references can be opened at
`/api/workflows/files/{fileId}`. Local CLI runs proxy to the same managed file API when connected.
Without a connection, creating a file throws instead of saving generated files locally.
Local resolution of input attachments continues through
`context.files.resolveFile(...)` work.

## Storage Recommendations

After upload, `await context.files.resolveFile(reference)` resolves a file on the same Server for `readBuffer()`, `readBase64()`, or `readDataUrl()`. The remote store authenticates against the fixed managed endpoint and never trusts a reference's URL or local path for authenticated reads.

Kanban pages use `createFile/readFile/deleteFile` on `window.steamHarnessKanban.knowledgeBases.get(alias).files` to access authorized knowledge-base attachments. See [Kanban data Bridge](/en/concepts/kanban#data-bridge).

Server saves knowledge images and other attachments in separate private file storage; PostgreSQL retains metadata, sizes and content digests. Every read checks the current binding and account grant; JSON transport uses Base64. Legacy inline KV attachments are not migrated automatically. Backups must retain both PostgreSQL and file storage.

Do not save base64 file contents into business rows or session history. Save the reference metadata returned by `file.toJSON()` when cross-round multiplexing is required.

Image workflows can resolve file parameters to `ResolvedFile[]` and pass `readBuffer()` or `readBase64()` results to an image service. Retain only `file.toJSON()` reference metadata across turns. To reuse generated images, save them with `context.files.createFile(...)` and return their references.

## CLI Web and server behavior

- A local CLI Web run uploads the attachment to local file storage, with `storage: "local"`.
- The server management interface `POST /api/workflows/{name}/files` saves project files with `storage: "server"`.
- Runtime-generated files use server file references. CLI Web and CLI upload them automatically when connected to Server and report an error when no Server connection is available.
- `GET /api/workflows/files/{fileId}` can read or download the server file.

If a Conversation declares `conversation.attachments`, its standard composer accepts pasted,
dropped, or uploaded images, videos, and files using the same file reference protocol. The host
writes each browser/Electron `File` to the local or server managed file store, then serializes
the reference under `--images`, `--videos`, or `--files`. The workflow reads these references with
[`workflow.parseConversationDefaultInputArgs(args)`](/en/core-api/parse-conversation-default-input-args).

Enable the dedicated video action with `attachments.videos: true`. Existing projects that only set
`files: true` continue to serialize videos under `--files`, preserving their session and file reference contract.

## MCP file parameters

Local stdio MCP file parameters accept absolute paths, with an array of absolute paths for multiple files. The host verifies regular files and the 50 MB limit before importing them into the local managed-file store. Relative paths, URLs, and Base64 are rejected.


## External API files

The outer Dify style `/workflows/run` receives the `files` field and saves it to the run metadata. Whether the specific workflow uses a file, it needs to be aligned by `inputs` or `args` and executor params.
