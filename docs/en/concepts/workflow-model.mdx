# Workflow model

A root `steamharness.json` identifies a project that can register several entries. Each entry declares its type, source, configuration, and resource requirements. `defaultEntry` selects the default entry; `entrypointId` separately selects an operation inside a Workflow.

The root `steamharness.json` is the only project configuration source. `package.json.id` and `package.json.steamHarness` are not read or supported. npm names and versions may differ from project names and versions. Root fields are `id`, `name`, `version`, `defaultEntry`, `entries`, and optional `description`, `projectCard`, `projectInfo`, `builtinRelease`.

The parent registers a child with only `{ "entryId": "agent", "root": "agent" }`. The child’s `steamharness.json` provides `type`, `name`, `entry`, `configuration`, `projectCard`, `projectInfo`, `databases`, and `schedulePresets`. Children cannot declare identity, version, or nested entries; paths are relative to the child directory. Unregistered children are never scanned or loaded. Root entries use `root: "."` and inline settings. Child references cannot override fields or inherit root settings. All referenced configuration files are required during upload, download, and built-in distribution.

## Workflow

A Workflow defines the business process through `steamharness.defineProject<Input, Output>()`:

```ts
export const exampleProject = steamharness.defineProject<Input, OutputPayload>({
  name: "example",
  async run(input, context) {
    const parsed = await steamharness.runNode(inputNode, input, context);
    const result = await steamharness.runStreamNode(outputNode, parsed, context);
    return result.output;
  },
});
```

`run` receives `input` and `context` and returns the final payload. If it throws, the executor serializes the error into the execution report.

## Node

A node is an executable unit for ordinary computation, streaming, branching, or looping:

```ts
const inputNode = steamharness.createInputNode<Input, Parsed>({
  name: "input",
  parse(input) {
    return { message: input.message.trim() };
  },
});

const outputNode = steamharness.createOutputNode<Parsed, OutputPayload>({
  name: "output",
  async *stream(input) {
    yield input.message;
  },
  format(stream) {
    return steamharness.createOutputPayload({
      items: stream.items,
    });
  },
});
```

### Execution and output

| API | Return value or recorded result |
| --- | --- |
| `runNode` | The node output |
| `runStreamNode` | `{ chunks, output }`; retains raw chunks and uses `finalize` or `format` for the final output |
| `createDetailsOutputNode` | Converts a title, content, and icon into an independent collapsed item, collected as a standard `output` node |
| `createTimerNode` / `endTimer` | Creates a standard `timer` node and records its end status and message in `report.timers` |

Running timers that were not ended become `cleared` before the Workflow finishes. For streaming `createOutputNode({ stream, format })`, `format` receives accumulated `{ text, items, chunks }`.

Output uses `RunOutputPayload.items: OutputItem[]`. Each item can be displayed and collapsed independently, with `id`, `title`, `content`, `contentType`, `collapsed`, `metadata`, and optional `icon` / `iconPreset` fields.

| `contentType` | Content requirements |
| --- | --- |
| `markdown`, `text`, `json` | Put objects and arrays directly in `content`; do not stringify them into Markdown code blocks |
| `audio` | `{ src, mimeType, name, size, durationMs?, format? }` with a safe audio data URL or HTTP(S) URL |
| `video` | An MP4 object containing `src`, `mimeType: "video/mp4"`, and `name`, with optional `durationMs` and `format: "mp4"` |

The browser's native player renders video. Missing required fields or unsafe URLs fall back to a text preview with `videoPlaybackUnsupported`. Do not pass an empty URL, `file://`, or `blob:`. Signed OSS URLs expire and are not cached; do not use them as the only published copy of an irreplaceable artifact. See [video output](/en/concepts/payloads-and-errors#video-output-item) for fields and persistence requirements.

### Streamed items and status

String chunks enter a default Markdown item. Use `createOutputItemChunk(...)` to emit `output_item_start`, `output_item_delta`, and `output_item_end`.

`output_item_delta` merges `content` and accepts an `item` patch for the title, icon, collapsed state, content type, and `metadata.status`. For example, a tool call can move from running to success or failed. See [output nodes](/en/core-api/create-output-node).

`runIf` evaluates branches in order and records the selected branch in a `branch-node` event. `runFor` and `runWhile` record loops as traceable nodes whose bodies remain visible in Diagram.

### User input and tool approval

1. Declare a human input point with `createUserInputNode`. Fields use the same definitions as the selected Workflow entrypoint or Conversation executor; CLI Web renders the same form.
2. For dynamic questions, provide a side-effect-free `resolveRequest(input, context)` that returns the title, description, fields, and defaults.
3. Without an answer, the run emits `user_input_requested`, includes `pendingUserInput` in its report, and enters `waiting_for_input`.
4. Submit answers to resume the same `runId` with `resolvedUserInputs`. This emits `user_input_resolved` and retains the snapshot's exact target and original entry.

The CLI does not read stdin. Submit answers with `steamharness json --run-id <id> --resolved-user-inputs-json '<json>'`; see [user input nodes](/en/core-api/create-user-input-node).

`createToolApprovalGate` uses the same wait/resume protocol. Register tools on the selected Workflow entrypoint or Conversation executor first. Unregistered tools return `input_validation`; disabled tools return `tool_permission_denied`. A tool that needs confirmation pauses the run with a `tool-approval` request. See [tool approval](/en/core-api/create-tool-approval-gate) for mode and policy rules.

## Branch

`steamharness.runIf` is suitable for writing business conditions as traceable workflow branches, rather than just plain TypeScript `if`:

```ts
const plan = await steamharness.runIf(seed, context, {
  name: "Weapon branch",
  branches: [
    {
      label: "high intensity assault",
      condition: (mission) => mission.intensity >= 0.66,
      run: (mission) => ({ ...mission, weapon: "ak47" }),
    },
    {
      label: "stealth close quarter",
      condition: (mission) => mission.stealth >= 0.58,
      run: (mission) => ({ ...mission, weapon: "mp7" }),
    },
  ],
  else: {
    label: "balanced rifle",
    run: (mission) => ({ ...mission, weapon: "m4a1" }),
  },
});
```

The first element in the `branches` array appears as `if` in Diagram, subsequent elements appear as `else-if`, and `else` appears as a fallback branch. The `run` of the branch can continue to call `steamharness.runNode`, `steamharness.runStreamNode`, or it can nest another `steamharness.runIf` to form a multi-level branch.

## Loop

`steamharness.runFor` and `steamharness.runWhile` are suitable for writing business loops as traceable workflow loops instead of just plain TypeScript `for`/`while`:

```ts
const rounded = await steamharness.runFor(seed, context, {
  name: "Round loop",
  maxIterations: 6,
  items: (state) => Array.from({ length: state.rounds }, (_, index) => index + 1),
  async run(state, value, index, loopContext) {
    return steamharness.runNode(addRoundNode, { ...state, value, index }, loopContext);
  },
});

const boosted = await steamharness.runWhile(rounded, context, {
  name: "Boost until target",
  maxIterations: 8,
  condition: (state) => state.total < state.target,
  async run(state, loopContext, iteration) {
    return steamharness.runIf(state, loopContext, {
      name: "Choose boost strategy",
      branches: [
        {
          label: "burst",
          condition: (current) => current.target - current.total >= 7,
          async run(current, branchContext) {
            return steamharness.runFor(current, branchContext, {
              name: "Burst passes",
              maxIterations: 3,
              items: () => [4, 3],
              async run(passState, value, index, passContext) {
                return steamharness.runNode(boostNode, { ...passState, value, index, iteration }, passContext);
              },
            });
          },
        },
      ],
      else: {
        label: "finish",
        async run(current, branchContext) {
          return steamharness.runNode(boostNode, { ...current, iteration }, branchContext);
        },
      },
    });
  },
});
```

`runFor` follows the iterable returned by `items`, with a default limit of `1000` iterations. `runWhile` checks `condition` before each iteration and defaults to `100`. Both callbacks return the state for the next iteration.

The completion event records `loopType`, `iterations`, `iterationCount`, `maxIterations`, and `completed` in `executionInfo`.

## Diagram and node protocol

The local host combines static structure with execution events in Diagram:

- **Static structure:** TypeScript analysis records known `steamharness.*` calls in `definitions.apiCalls`, including `createInputNode`, `defineProject`, and `getConfig`. These show which APIs the source uses; they are not independent executions on the `Input -> Result` path.
- **Execution state:** `nodeHooks` from `runNode`, `runStreamNode`, `runIf`, `runFor`, `runWhile`, and `runProject` provide status, elapsed time, and errors for nodes that actually run.

### Branches and loops

Diagram displays `runIf` as a `run-if` node with a branch icon and semantic color. Trace reads `selectedBranch`, `selectedBranchIndex`, and `description` from the completion event.

Static analysis can expand object-literal `branches` / `else` declarations. Dynamically constructed branches still run, but their full paths may not appear in Diagram.

`runFor` and `runWhile` appear as `run-for` and `run-while` nodes, with their bodies grouped in colored rectangles. Select the loop header to inspect `items`, `condition`, `maxIterations`, and iteration results.

Loop bodies can contain branches or nested loops. Static analysis expands literal loop options; dynamic options can run without a complete visual expansion.

### Nested Workflows

`runProject` appears as a `run-workflow` node. Child events join the parent trace rather than creating a separate report. The top-level executor does not add this wrapper node.

Defaults are `conversationMode: "shared"` and `outputVisibility: "visible"`; setting only `name` changes neither. With `conversationMode: "shared-readonly"`, the child can read the parent snapshot but cannot append transcript messages or change its title.

Entrypoints form one flat set of independent operations, not nested Diagram nodes. Use nested `runProject()` calls for multiple levels of orchestration; the default maximum depth is `16`.

### Custom node protocol

Built-in ordinary nodes inherit `BaseNode`; streaming nodes inherit `BaseStreamNode`. Both expose `name`, `standardName`, `metadata`, and `getExecutionInfo()`.

Diagram consumes the `NodeDefinition` / `StreamNodeDefinition` execution protocols and run reports, rather than binding directly to these classes. Custom nodes that implement the protocols can also be executed and recorded.

## Provider

The executor currently has one built-in provider name, `"llm"`. Resolve its configuration at execution time through `createLLMProviderRef`:

```ts
const llmProvider = steamharness.createLLMProviderRef("default", () => {
  return steamharness.createLLMProviderFromConfig();
});
```

Project business values come from [Project configurations](/en/concepts/project-configuration), without project env loading or process-variable fallback. Host deployment and transport settings remain separate.

## Executor

An executor is the project's static execution configuration. Hosts use it to discover the project and run it. A Workflow project declares one default entrypoint and any number of independently runnable entrypoints:

```ts
export const executor = steamharness.defineExecutor<Input, OutputPayload>({
  projectType: "workflow",
  defaultEntrypoint: "main",
  entrypoints: [
    steamharness.defineEntrypoint<Input, OutputPayload>({
      id: "main",
      title: "Complete workflow",
      group: { id: "operations", title: "Operations", order: 10 },
      workflow: exampleProject,
      params: [
        {
          name: "message",
          flag: "--message",
          type: "string",
          required: true,
          description: "Input text.",
        },
      ],
      createInput({ args }) {
        return parseArgs(args);
      },
    }),
  ],
});
```

Selecting or requesting an entrypoint creates a run only for that entrypoint; it does not run `main` first. Entry IDs are unique within the project and must match `/^[a-z][a-z0-9_-]{0,63}$/`. `entrypoints` must be a non-empty static array, and `defaultEntrypoint` must name one of its entries. Each entrypoint independently declares its `workflow`, `params`, `resolveParams`, `createInput`, provider, tools, token usage, registry, and context factory.

An entrypoint may also declare static `group: { id, title, order? }` metadata: `id` and `title` must be non-empty strings and `order` must be a non-negative integer. All entries sharing a group ID must use exactly the same title and order, including whether `order` is omitted. Legacy top-level Workflow execution fields are no longer accepted.

When any explicit group exists, the local Run workspace renders entrypoints in collapsible groups. Explicit orders sort ascending with first-seen order as the tie breaker; groups without an order follow in first-seen order, and entries without a group use a localized **Ungrouped** group. The default group is open on first entry, and starting a run or receiving a new active/result entry reopens its group. Only group expansion is persisted by stable `projectId + resolved target`. Projects without groups retain the existing flat layout. CLI and local schedules continue to use entrypoint IDs.

Projects can use `steamharness.json.entries[].schedulePresets` to propose schedules for an entrypoint. Structure validation checks the preset ID, entrypoint, time zone, trigger rule, and JSON parameters, then exposes the presets to the local host. Presets are not enabled automatically. See [Workflow scheduled runs](/en/concepts/workflow-schedules).

Conversation executor keeps a single entry, places fields such as `workflow`, `params`, and `createInput` directly on executor, and does not declare or accept entrypoint. `projectType` of Executor only allows `"workflow"` or `"conversation"`. Kanban registers static HTML in root `steamharness.json.entries` and does not export an executor.

`createInput` receives `projectName`, `projectDir`, `args`, `paramValues`, `config`, `abortSignal`, and optional `conversationId`. Workflow also receives the selected `entrypointId` and `entrypointTitle`; the same fields are written to `RunContext.metadata`, reports, and local run records. The local host converts parameters to workflow input through the selected execution configuration. Cancellation propagates `abortSignal` to the workflow context so long-running provider and SDK calls can stop promptly.

`resolveParams` can return `value`, `visible`, `disabled`, and a single option status patch as the current parameter, or replace the current full list of options for the parameter with an `resolvedOptions` array, or restore the static options with `null`. Initialization and changes to the Form parameters of main, Advanced, and Quick will trigger evaluation.

`visible: false` does not implicitly empty old values; mutex parameters should also return `value: null` to prevent hidden values from continuing into `args` and `paramValues`. Dynamic lists are suitable for reading provider, model, or variant directories provided by the server; reads must be cancelable, time-limited, and run data cannot be written during parameter evaluation.

## Registry

Registry is used for single-node debugging and structure demonstration. The registry of Workflow belongs to the concrete entrypoint and must be a static array literal:

```ts
export const executor = steamharness.defineExecutor<Input, OutputPayload>({
  projectType: "workflow",
  defaultEntrypoint: "main",
  entrypoints: [
    steamharness.defineEntrypoint({
      id: "main",
      title: "Complete workflow",
      workflow: exampleProject,
      registry: [
        {
          name: "output",
          node: outputNode,
          stream: true,
          metadata: { type: "output", title: "Output", version: "1.0.0" },
          createInput({ args }) {
            return parseArgs(args);
          },
        },
      ],
      createInput({ args }) {
        return parseArgs(args);
      },
    }),
  ],
});
```

Local CLI `debug-node` uses the selected entrypoint registry to debug one node. Omitting the entry selects the default and never searches other entrypoints. Conversation uses its executor-level registry.


```json
{
  "version": 1,
  "databases": {
    "data": "00000000-0000-4000-8000-000000000001"
  }
}
```

Each entry can configure `projectCard.icon`, `iconColor` and `iconBackgroundColor`, using `#RRGGBB` colors. Omitted properties use entry type defaults and do not inherit the root avatar. Entry lists carry these icons to window panels, tabs, Server and Store. The root `steamharness.json.projectCard` identifies the aggregate. Only root `steamharness.json.version` owns a version; entry declarations reject `version`.

Paths must stay inside the aggregate directory and cannot contain `..`, absolute paths or host data directories. Static analysis scans each registered entry independently, allowing different executors in one aggregate. Each Workflow or Conversation executor must match its registered type; Kanban points to built HTML. Only the root owns the SteamHarness identity. Child directories retain ordinary npm packages and dependencies.

Legacy root type, storage-location and project-relationship declarations are rejected. Use fresh declarations and data, [independent spaces](/en/concepts/data-storage), and `context.entries.get(entryId)` for calls within the aggregate.
