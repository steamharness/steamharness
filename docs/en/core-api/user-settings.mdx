# User settings and permission inheritance

User settings belong to the execution host and are stored separately from project configuration and turn parameters. Studio saves the user's Agent permission in **Settings → Permissions**, defaulting to `auto`. Workspace settings cannot override it. Ordinary Agents still default to `workspace`; they read user settings only when explicitly configured with `inherit`.

## Public API

```ts
interface UserSettings {
  readonly agent: {
    readonly permissionPolicy: AgentPermissionPolicy;
    readonly models?: readonly Readonly<UserAgentModel>[];
  };
}

type AgentPermissionPolicy = "read-only" | "workspace" | "auto";
type AgentPermissionPolicySetting = AgentPermissionPolicy | "inherit";

getUserSettings(): UserSettings;
parseUserSettings(value: unknown): UserSettings;
withUserSettings<T>(settings: UserSettings, run: () => T): T;
```

Projects read settings through the injected `steamharness.getUserSettings()`. Hosts import these APIs from the `steamharness` package. `parseUserSettings` and `withUserSettings` serve host injection and are not members of the project runtime namespace.

`getUserSettings()` returns a copied, deeply frozen snapshot. Without a host it returns `{ agent: { permissionPolicy: "auto" } }`. `parseUserSettings` and `withUserSettings` accept only the three concrete policies; missing fields, `inherit`, and other invalid values throw `TypeError`. Mutating the original host object does not change an already started task.

```ts
// Project code: read the snapshot or let Core resolve inheritance.
const settings = steamharness.getUserSettings();
const agent = await steamharness.createAgent({ permissionPolicy: "inherit" });
try {
  for await (const event of agent.run({ errCode: 0, errMessage: "", prompt: "Inspect the project", permissionPolicy: "inherit" })) {
    // Handle events.
  }
} finally {
  await agent.close();
}
```

```ts
// Host code: asynchronous descendants share this snapshot; concurrent runs stay isolated.
import { withUserSettings } from "steamharness";

await withUserSettings({ agent: { permissionPolicy: "read-only" } }, async () => {
  await runProject(); // The host's own execution entry point.
});
```

## Resolution order

Core first selects `AgentInput.permissionPolicy` for the turn, then the developer's runtime or node `permissionPolicy`. If both are omitted it uses `workspace`. A selected `inherit` resolves to the concrete policy in the current user snapshot, or `auto` without a host. Direct Agent calls, Agent nodes, and project parameters follow the same rules.

Direct callers may still pass `--permission-policy inherit`. Parameter forms preserve an empty override marker for inherited fields and save concrete values only after an explicit project selection. Tool filtering, file scope, and runtime initialization receive only the resolved concrete value. See [createAgent permission policy](/en/core-api/create-agent#permission-policy) for tool, path, and shell behavior.

## Parameter presentation

Use `ParamDefinition.userSetting` to choose how a project uses a user setting. Single string fields support `key: "agent.permissionPolicy"` or `key: "agent.model"`.

- `mode: "fixed"`: show only the effective policy and open Studio user settings when clicked. Project overrides, including previously saved values, are ignored.
- `mode: "default"` (also the omitted mode): retain the original three choices and select the current user policy by default. A selection becomes a project override; reset restores the current user default.

Declare the binding inline and omit `defaultValue`. Multiple values, checkboxes, Mode, and Slash fields cannot bind a user setting. `paramValues` receives the effective value in the execution snapshot.

```ts
params: [{
  kind: "quick", id: "permission", label: "Permission", icon: "shield",
  summary: ["permissionPolicy"],
  fields: [{
    name: "permissionPolicy", flag: "--permission-policy", type: "string",
    control: "select",
    userSetting: { key: "agent.permissionPolicy", mode: "fixed" },
    options: [
      { value: "read-only", label: "Read only" },
      { value: "workspace", label: "Workspace" },
      { value: "auto", label: "Auto approve" },
    ],
  }],
}],
createInput({ paramValues }) {
  return { errCode: 0, errMessage: "", permissionPolicy: paramValues.permissionPolicy };
}
```

Change the example to `mode: "default"` to allow project overrides. `createAgentProjectParams({ permissionPolicy: "inherit" })` generates that editable binding. Standalone CLI can resolve injected settings, but opening the settings page requires Studio.

## User models and Agents without connection configuration

Use **Settings → Models** to add, edit, delete, and set a default model across workspaces. The host supplies each model's name, protocol, Base URL, model ID, and API key to execution. Third-party keys live in Studio SecretStorage and are excluded from project configuration, page state, ordinary conversation history, and exports. An empty key when editing keeps the saved key.

Open-source Studio offers third-party models only: OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages. Hosts providing system AI may also expose their authorized catalogue. System entries save credential and model IDs; execution rechecks account authorization and model availability without persisting proxy tokens.

`UserAgentModel` is a union of two records, each with a stable `id`, display `name`, and actual `model` ID:

- System: `{ source: "system", credentialId: string }`.
- Third-party: `{ source: "third-party", apiKind: "openai-completions" | "openai-responses" | "anthropic-messages", baseUrl: string, apiKey: string }`.

Lists are copied and frozen. Base URLs require HTTP(S) without authentication, query, or fragment; entry IDs must be unique, with at most 100 entries. Invalid model configurations are rejected.

With a nonempty user list, Agent nodes and direct `createAgent()` automatically select the first permitted model; turn `model` can select a list ID. Explicit developer endpoints, `models`, and `resolvedModel` keep their existing behavior. `modelSource: "user-settings"` requires user models and reports an empty list; `modelSource: "project"` explicitly retains the original project configuration source. A project's `allowThirdParty: false` applies to user models and explicit endpoints alike.

```ts
// Generate overridable model parameters from the user's list and default.
const project = steamharness.createAgentConversationProject({
  modelSource: "user-settings",
  permissionPolicy: "inherit",
});

// Custom parameter declarations may bind inline:
// userSetting: { key: "agent.model", mode: "default" }
// resolveParams: steamharness.createAgentProjectParamResolver({ modelSource: "user-settings" })
```

`createAgentProjectParams()` also generates the user model binding by default. When automatically using user models, the resolver preserves an empty override so later user default changes still apply. Pass `modelSource: "project"` explicitly to generate the original project model controls. A model ID named `inherit` is an ordinary ID; permission inheritance still uses `permissionPolicy: "inherit"`.

Reused third-party connections retain developer `modelAttributes` defaults. System catalogue search restrictions remain authoritative and cannot be enabled through turn attribute overrides.

The built-in assistant uses user models. Clicking its model control opens available choices first; **Manage models** opens settings. Selecting a model overrides the default for the project or conversation; resetting follows the user default again. The original project model configuration APIs remain available and are not used by the assistant.

With no available models, the control shows **Configure model** and guidance to add a model in settings. Clicking it opens **Settings → Models** directly; adding a model restores the choices.

A custom model field with `mode: "fixed"` also opens the list first, with read-only choices and a **Manage models** action to change the user default. `mode: "default"` allows a project override.

Updates apply after a safe task boundary. Active and background work retain their connection snapshot. A directly created Agent with a host-resolved model also resolves inherited permissions from that creation snapshot; explicit turn permissions still take precedence. Recreate the Agent after its work finishes to adopt new host model settings. Interrupted recovery obtains a key from the host only for the same model and endpoint; a removed or changed endpoint fails explicitly instead of receiving a new key at an old address.

## Studio and CLI sessions

Studio's built-in assistant uses a fixed user-setting binding. Its permission control shows the actual policy (for example, **Auto approve**) and opens **Settings → Permissions** when clicked. There is no additional inheritance choice. Saved session overrides cannot change a fixed binding. Coding tools, the system prompt, and Studio Control use the same settings snapshot.

After a settings change, active tasks, background work, and child tasks keep their original snapshot. Once all work finishes and a durable session is idle, the host remounts the original database with the latest settings. New input waits for that boundary, preserving history, queues, and request identities. Interrupted work first resumes with its recorded startup snapshot.

CLI Web accepts initial host settings and updates after a capability handshake. Older CLIs do not receive update messages; update the project's Core and CLI to use inheritance. Standalone CLI does not persist this preference in this release; without host injection `inherit` uses `auto`.
