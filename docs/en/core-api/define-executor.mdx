# defineExecutor

Use `steamharness.defineExecutor()` to declare how a project receives input and starts execution. Workflow declares a default operation and `entrypoints`; Conversation declares its workflow, parameters, and input constructor directly on the executor.

## Example

```ts
export const executor = steamharness.defineExecutor<Input, Output>({
  projectType: "workflow",
  defaultEntrypoint: "main",
  entrypoints: [
    steamharness.defineEntrypoint<Input, Output>({
      id: "main",
      title: "Full workflow",
      workflow: exampleProject,
      tokenUsage: { enabled: true, display: true },
      tools: [
        {
          name: "search",
          label: "Search",
          description: "Calls an external search tool.",
          enabled: true,
          autoApprove: false,
        },
      ],
      params: [
        {
          name: "message",
          flag: "--message",
          type: "string",
          required: true,
          control: "textarea",
          description: "Input text.",
        },
      ],
      createInput({ args }) {
        return { message: readMessage(args) };
      },
    }),
  ],
});
```

## Signature

```ts
steamharness.defineExecutor<Input, Output>(
  definition: ExecutorDefinition<Input, Output>,
): ExecutorDefinition<Input, Output>
```

## Parameter

|Parameter|Type|Description|
| --- | --- | --- |
| `definition` | `ExecutorDefinition<Input, Output>` |Platform discovery and implementation of ingress configuration for workflow.|

## Workflow executor

|Field|Type|Description|
| --- | --- | --- |
| `projectType` | `"workflow"` |The project type. Required.|
| `defaultEntrypoint` | `string` |The entrypoint ID used when no entrypoint is selected. It must be a string literal that names an item in `entrypoints`.|
| `entrypoints` | `EntrypointDefinition[]` |A non-empty array of static entrypoint definitions. Each item must call [`steamharness.defineEntrypoint()`](/en/core-api/define-entrypoint) directly.|

`workflow`, `params`, `createInput`, `resolveParams`, `createContext`, `requiredProviders`, `tools`, `tokenUsage`, and `registry` are entrypoint-specific Workflow fields and cannot appear at the top level of an executor. Hosts display entrypoints in declaration order. Selecting one creates a run for that entrypoint directly; the default entrypoint does not run first.

Workflow can declare the proposed schedule in `steamharness.json.entries[].schedulePresets`. Each entry statically references a entrypoint and contains a IANA time zone, time window, or 5 field Cron, and default parameter values. The directory goes into the Structure report, but the host must display a confirmation interface and cannot automatically create a schedule for importing or publishing a project. Conversation and Kanban declare this field to be rejected by Structure. See [Workflow Timed Run](/en/concepts/workflow-schedules) for the full format and run boundaries.

## Conversation executor

|Field|Type|Description|
| --- | --- | --- |
| `projectType` | `"conversation"` |The type tag for the Conversation item. Required.|
| `workflow` | `Definition<Input, Output>` |Conversation is unique to workflow. Required.|
| `createInput` | `(context) => Input` |Converts args, configuration snapshots, and session IDs into business inputs. Required.|
| `resolveParams` | `(context) => ParamResolveResult` |Optional parameter linkage callback.|
| `createContext` | `(context) => Partial<RunContext>` |Add providers, metadata and hooks.|
| `requiredProviders` | `ExecutorProviderName[]` |Declares a required provider.|
| `params` | `ConversationParamDeclaration[]` | Ordered Conversation Auxiliary, Quick, Mode, and Slash entries. |
| `tools` | `ToolPermissionDefinition[]` |Conversation Callable tools and default policies.|
| `conversation` | `ConversationDefinition` | Configure attachments, the input queue, and the optional OpenAI gateway. The standard message input needs no configuration. |
| `tokenUsage` | `TokenUsageDefinition` |Enable token usage statistics.|
| `registry` | `NodeRegistryEntry[]` |Register nodes that can be debugged individually.|

Conversation does not declare `defaultEntrypoint` or `entrypoints`. CLI rejects a non-empty entrypoint selection instead of silently ignoring it.

Durable Agent projects can declare inline `conversation.recovery: { enabled: true }` and `conversation.durable: { enabled: true }` alongside Agent `session` options. Recovery enables host crash recovery; durable enables the Harness inbox, bidirectional controls and persistent owner in CLI Web / Studio, with complete task views in Studio Trace. Harness persists steer / followUp / reject submissions and withdrawals. `defineAgentConversationExecutor({ session })` adds durable automatically; static structure projects must still declare inline objects. Explicit `tools` lists must include `update_plan` and, when enabled, `subagent`. See [session control](/en/core-api/create-agent#durable-session-control). Local CLI / Studio hosts execute projects; Server only manages projects and data.

## `ExecutorContext`

|Field|Type|Description|
| --- | --- | --- |
| `projectName` | `string` |The current workflow name.|
| `projectDir` | `string` |The current workflow directory.|
| `entrypointId` | `string \| undefined` | The selected Workflow entry-point ID; `undefined` for Conversation. |
| `entrypointTitle` | `string \| undefined` | The selected Workflow entry-point title; `undefined` for Conversation. |
| `args` | `string[]` |Original CLI style parameter.|
| `paramValues` | `Record<string, string \| string[]>` |The structured value after parsing by `params`. A single value holds a string, and multiple values are selected as a string array.|
| `env` | `NodeJS.ProcessEnv` |A collection of environment variables.|
| `abortSignal` | `AbortSignal` | An interrupt signal; CLI Web cancellation is passed to workflow and SDK/provider calls that support signals. |
| `conversationId` | `string \| undefined` |The session ID.|
| `toolPermissionPolicies` | `ToolPermissionPolicyMap \| undefined` |The tool policy override value passed in by the host. workflow usually does not read this field directly, but uses `context.toolPermissions` or `steamharness.createToolApprovalGate()`.|

## Execution process

|Phase|Description|
| --- | --- |
|Platform Selection Configuration|Workflow selects an entry by explicit ID or `defaultEntrypoint`;Conversation uses executor itself.|
|Create Context|runtime creates a `ExecutorContext` based on args, env, projectName, entry, and conversationId.|
| `createInput` |Invokes the input construct of the selected entry or Conversation executor.|
| `createContext` |An optional context extension that invokes the same execution configuration.|
| workflow `run` |Execute only the workflow of the selected entry, or the only workflow of Conversation.|

## Tool permissions

`tools` Default permission for registering workflow business tools. Each tool contains stable `name`, and optional `label`, `description`, `enabled`, and `autoApprove`. `enabled` default `true`,`autoApprove` default `false`. CLI Web can cache user selections and pass in override values before running;runtime only accepts `enabled/autoApprove` overrides for registered tools, and unknown tools are ignored.

code running in a workflow can use [`steamharness.createToolApprovalGate()](/en/core-api/create-tool-approval-gate) to wrap tool functions. When the tool is not registered, it will fail as `input_validation`; When the tool is disabled, it will be rejected as `tool_permission_denied`; When the tool is enabled but not automatically approved, the waiting/recovery protocol of `steamharness.createUserInputNode(...)` will be reused to generate a `tool-approval` request. After approval, the same run will continue and `tool_permission_denied` will be returned after rejection.

## Precautions

|Rules|Description|
| --- | --- |
|`createInput` is required|Each Workflow entrypoint and Conversation executor must be declared.|
|`paramValues` is a formal structured value|`createInput` can read parameter values directly;`args` continues to be used in scenarios that require full CLI parameters or unknown parameters.|
|Workflow The running configuration belongs to entrypoint|The top-level old field gives a migration error and no longer retains the compatible alias.|
|`tools` must be statically declared|CLI Web can only show the selected entry or Conversation executor statically analyzed tools; the tool name must be stable.|
|`tokenUsage.enabled` Off by default|If it is not configured, platform usage records will not be written and the usage will not be displayed. When closed `context.tokenUsage.report()` is no-op.|
|`registry` for single node debugging|Workflow searches only the registry of the selected portal; nodes that are not registered cannot be run individually through debug API.|
