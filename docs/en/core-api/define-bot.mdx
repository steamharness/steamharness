---
title: "defineBot"
description: "Declare a Bot entry backed by Core Agent or an LLM, and configure its tools."
---

Use `steamharness.defineBot()` and register the entry in `steamharness.json` with `type: "bot"`. The declaration requires an `engine`. Add `engine: "agent"` to existing declarations to keep their behavior.

You cannot switch engines within a conversation. After changing the project's `engine`, reopen it to start a new conversation. You can still read the old history.

| Engine | When to use it | Engine-specific options |
| --- | --- | --- |
| `"agent"` | Handle multi-step work or use planning, memory, and durable recovery. | `agent`, `memory` |
| `"llm"` | Answer from the current conversation or call tools without starting an Agent. | `llm` (required; pass `{}` for defaults) |

Both engines accept `name`, `params`, `resolveParams`, `conversation`, `tools`, `prepareInput`, and `onCompleted`. They return a `BotExecutorDefinition` with `AgentOutputPayload` and a final answer item named `agent-answer`. You cannot override `workflow`, `coreAgent`, `createInput`, `tokenUsage`, or `outputItemId`.

## LLM Bot

```ts
export const executor = steamharness.defineBot({
  engine: "llm",
  llm: { systemPrompt: "You are a project assistant." },
});
export default executor;
```

LLM Bots send the completed turns and current input to the model and stream the answer. The OpenAI Responses adapter uses only the history provided in the request. LLM Bots support text, images, queues, and stopping. They do not start an Agent or use planning, subagents, project memory, or built-in web search.

A turn takes one model request unless the model calls a tool. Core validates the arguments and permissions, then sends the tool result back to the same model. The answer's usage covers all model requests in the turn. Tool calls and results are not carried into the next turn.

Local debugging hosts can pass `nodeHooks.onLLMBotModelRequest` to `runLocalProjectWithReport()` to inspect each dispatch. The `LLMBotModelRequestSnapshot` includes the provider, model, protocol, system prompt, messages, tool declarations, and dispatched generation settings. Images retain only their media type. Core keeps snapshots out of ordinary reports and events. Restrict access to debug views: snapshots can contain private messages and tool results.

| `llm` option | Type | Purpose |
| --- | --- | --- |
| `systemPrompt` | `string` | System prompt shared across turns. |
| `modelSource` | `"user-settings"` or `"project"` | Select models from host settings or project configuration. |
| `model` | `string` | Default model entry ID. Omit to use the configured default. |
| `temperature` | `number` | Optional non-negative sampling temperature, where supported. |
| `maxOutputTokens` | `number` | Optional positive integer cap on output tokens. |
| `createTools` | Function returning `AgentTool[]` or `AgentToolSet`, optionally async | Creates tools for the turn from `context` and the prepared input. Core calls `close()` at the end of the turn if provided. |

Core saves the completed turn by `requestId` before calling `onCompleted`. When the callback fails, retrying that request replays the saved answer and retries only the callback. An interrupted stream is not saved as a completed turn or sent again automatically. Before retrying manually, check whether any tools already took effect.

### Use tools in an LLM Bot

Open **Project information → Tools** in Studio or CLI Web to enable tools and set which ones need approval. Only `runtime_info` is enabled and auto-approved by default. Ask, “Where is this Bot running, and what version of Core is it using?” The tool reports the SteamHarness execution host, loaded versions, OS, and project entry, not local absolute paths, credentials, or the model server's location.

File, search, wait, and shell tools are off by default. File tools stay within the current entry directory; `bash` runs with the host process's permissions and is not sandboxed. To add a project tool, declare its name and defaults in top-level `tools`, then return an implementation with the same name from `llm.createTools`. Structure inspection reads the declarations without running the factory.

The model endpoint must support tool calling. With **Auto-approve** turned off in Studio or CLI Web, each call waits for confirmation. Approval continues the same turn; rejection ends it. Hosts without interactive approval, such as the OpenAI Responses entry or direct CLI runs, can run only auto-approved tools. For a model endpoint without tool support, set `tools: [{ name: "runtime_info", enabled: false }]` and leave the other tools disabled.

## Agent Bot

Configure models, prompts, skills, permissions, tools and sessions through `agent`. Core provides Model, Effort, Plan and permission parameters. Customize them through `agent.paramOptions`; top-level `params` adds business fields without replacing reserved fields. Fixed values remain enforced after input preparation.

`agent.createTools(context, input)` and `agent.createSession(context, input)` receive prepared input. Agent Bots support durability and recovery; choose `"automatic"` or `"manual"` via `conversation.recovery.startup`. Both engines accept `conversation` options for presentation, commands, and input interactions.

`prepareInput(input, context)` runs after Core parses text and images and returns an extended `AgentInput`. The context exposes configuration, `args`, `paramValues`, and cancellation. `onCompleted({ requestId, output }, context)` receives a read-only successful result and must return `void`. Use `requestId` as the idempotency key for any business receipt.

```ts
export const executor = steamharness.defineBot({
  engine: "agent",
  name: "assistant",
  agent: { systemPrompt: "You are a project assistant." },
  async prepareInput(input, context) {
    return { ...input, systemPrompt: String(context.config.instructions ?? "You are a project assistant.") };
  },
});
export default executor;
```

Both engines use the same [model and credential configuration](/en/concepts/project-configuration). They default to Studio user settings, or project configuration in standalone CLI Web. Set `modelSource: "project"` to require project models. System AI and third-party models are subject to the project's model source policy. Authentication failure does not select a different model. Local runs may omit the project `id`; release builds validate the project UUID.

Tools retain Core Plan/Build approval behavior by default. For operations that must also ask in Build mode, declare `tools[].approvalMode: "always"` with `autoApprove: false`. Queries can use `autoApprove: true`. Omitted approvalMode, or `approvalMode: "plan"`, preserves mode-based approval.

While an Agent Bot waits for tool approval in Studio or CLI Web, you can read the text it wrote before requesting the tool. Choose **Stop** to cancel the pending approval. The tool does not run, and earlier messages stay in the conversation.

## Project memory

Agent Bots enable project memory by default. Conversations in the same project and Bot entry share memories. Other projects and entries have separate storage. Each entry has a `category` and `key`, so project facts, decisions and procedures can be kept apart.

Open the active configuration under **Project configurations**, toggle **Bot memory**, and save. Subsequent executions use the setting; saved run snapshots keep their original configuration. Turning memory off removes its tools and guidance from that execution while preserving saved entries. Turn it on again to retrieve them.

`memory.enabled` sets the initial default and defaults to `true`. Saved project configuration takes precedence over the source default. This declaration starts new configurations with memory off; users can still enable it in the interface:

```ts
export const executor = steamharness.defineBot({
  engine: "agent",
  memory: { enabled: false },
  agent: { systemPrompt: "You are a project assistant." },
});
```

The boolean configuration key is `STEAMHARNESS_BOT_MEMORY_ENABLED`; you usually do not need to declare it in `configuration.json`. An explicit declaration must use type `boolean`. If `defaultValue` is omitted, it inherits `memory.enabled` from the Bot exported by that entry. Other Bot declarations do not change this default.

Core provides these tools alongside business tools supplied by `agent.extraTools` and `agent.createTools`. A conflicting memory tool name in either place causes an execution error:

| Tool | Arguments and result |
| --- | --- |
| `memory_save` | Pass `category`, `key`, and at least one of `content`, `title`, `summary`, or nonempty `properties`. Returns a stable `id` and `revision`. It does not overwrite an existing category/key. |
| `memory_get` | Read one entry by `id` or by `category` and `key`. Optionally set `relations` to `"outgoing"` or `"incoming"`. Returns `memory: null` if the entry is missing. `category`, `query` or `where` lists summaries. With no filters, the tool lists categories. |
| `memory_search` | Pass `keywords` and optionally `category`, `where`, `match`, `limit` and `offset`. Matches keywords against category, key, title, summary and body, then ranks results by keyword coverage and relevance. |
| `memory_update` | Select an entry by `id` or by `category` and `key`. Pass `expectedRevision` and only the fields to change. Returns the new revision. |
| `memory_delete` | Select an entry by `id` or by `category` and `key`, and pass `expectedRevision`. Deletion is blocked while other memories reference the entry. Deletion removes its outgoing links but keeps their targets. |
| `memory_link` / `memory_unlink` | Pass `sourceId`, `targetId`, `relation` (for example, `depends_on`) and the source's `expectedRevision`. Adds or removes one directed link and returns the source's new revision. |

### Structured memories and links

Give objects that change independently their own entries. For example, store the release center's `title` and `properties: { status: "live" }` on one entry. The deployment procedure and release notes can each link to its `id`. Update the release center once and both links return its current name and status. Text already written into other entries does not change; use it for dated historical facts when needed.

`properties` is a JSON object with a limit of 4,000 serialized characters per entry. Updates replace individual top-level values and leave other keys alone. Use `removeProperties` to remove keys. A property can store `null`; for `title`, `summary` and `content`, passing `null` clears the field. `where` requires an exact match on every supplied top-level key. It accepts strings, numbers, booleans and `null`; a missing key does not match `null`.

In `memory_get`, `outgoing` lists the entries this memory references, and `incoming` lists the entries that reference it. Results include current properties but not the bodies of linked entries, and expand only one level. The default is 5 links with a maximum of 10 per page. Use `nextOffset` when another page is available. Before deleting a referenced entry, inspect incoming links and remove the links that should no longer exist.

At the start of each turn, Core extracts keywords from the current input and retrieves relevant memories before calling the model. Later model requests refresh the results so edited or deleted excerpts do not remain in context. Follow-up messages, steering inputs and resumed execution also use the current input. Background retrieval runs only when the search tool is enabled and auto-approved; it never opens a confirmation dialog.

`memory_search` returns up to 5 entries by default, with a maximum `limit` of 10. Each excerpt contains at most 240 characters around a matching passage, and the complete search result stays within 6,000 characters. Pass up to 12 keywords, each at most 80 characters and at most 500 characters combined. `any` (the default) matches one or more keywords; `all` requires every keyword. Matching is literal and supports Chinese.

Search results include `id`, category, key, revision and matched keywords, plus the title and summary if set. Use `memory_get` to read a relevant entry in full. A body can contain up to 8,000 characters. When more results exist, `nextOffset` provides the next `offset`. Prefer narrower keywords over paging through every memory.

Category and summary lists from `memory_get` accept `limit` (default 10, maximum 20) and `offset`. `query` accepts up to 12 whitespace-separated terms that must all match. Excerpts take the first 240 characters of the body.

Before updating, deleting or changing a link, read the entry being modified and pass its `revision` as `expectedRevision`. On a version conflict, retrieve the latest entry before deciding what to change. Tools retain host permission and approval checks. Plan and read-only runs offer `memory_get` and `memory_search` only.

Core's built-in guidance tells the Bot to maintain memory silently. It judges whether confirmed project facts, decisions, procedures or preferences will help future conversations and saves them without waiting for a request to remember. It checks for duplicates, updates changed facts and deletes facts confirmed obsolete or explicitly forgotten, without routine confirmation or memory announcements.

The model decides what to retain from the conversation; it does not copy every message. Stored content is reference data and cannot override current instructions. Credentials, full transcripts, transient progress, guesses and information the user explicitly asks not to retain should not be stored.

Memories persist in SQLite on the execution host. Older databases upgrade on first access, keeping their entries and the existing `category` and `key` calls. Memories persist across conversations and restarts on that host, with no account-level memory or synchronization between machines. Separate runtime data directories, source runs and release runs keep separate memories. Exporting, copying or deleting a conversation does not copy or delete project memories, and project release archives exclude memory content.

## Skills and host previews

List skill directories under `agent.skills.directories`. Relative paths resolve from the current entry root. When directories contain skills with the same name, the first one wins.

Core supplies the `skill` tool automatically; projects can adjust its permissions through `tools`. Host previews read configuration declarations without executing input hooks or tool factories.

```ts
export const executor = steamharness.defineBot({
  engine: "agent",
  agent: { skills: { directories: ["skills"] } },
});
```
