# Knowledge Documents

Access Server-managed knowledge with `context.knowledgeBases.get(alias)`. Documents, indexes, and attachment metadata are isolated by knowledge-base ID; attachment bytes use private file storage. A knowledge base requires no business schema and creates no physical database per project.

## Create and bind

Sign in with `steamharness workspace login`, then create and bind a resource:

```sh
steamharness knowledge create "Project docs"
steamharness knowledge bind . --entry main --alias docs --knowledge-base <UUID>
steamharness knowledge bindings . --entry main
```

The bind command records an account/project/entry/alias binding on Server, adds `"knowledgeBases": ["docs"]` to the entry declaration and stores `"knowledgeBases": {"docs": "<UUID>"}` in root `config.json`. `STEAMHARNESS_PROJECT_CONFIG` can override IDs by knowledge alias. Configuration contains no credentials and grants no access. See [project storage](/en/concepts/data-storage).

## Documents and concurrent changes

```ts
const knowledge = context.knowledgeBases.get("docs");
const created = await knowledge.createDocument({
  id: "guide", title: "Guide", markdown: "# Guide\nHello 世界",
});
const current = await knowledge.getDocument(created.id);
if (current) {
  await knowledge.editDocument({
    id: current.id, markdown: "# Updated guide", expectedRevision: current.revision,
  });
}
const page = await knowledge.listDocuments({ pageSize: 20 });
if (page.nextCursor) {
  const next = await knowledge.listDocuments({ pageSize: 20, cursor: page.nextCursor });
}
const matches = await knowledge.searchDocuments({ query: "世界", pageSize: 20 });
const lines = await knowledge.readDocumentLines({ documentId: "guide", startLine: 1, endLine: 10 });
```

### Results and pagination

| Result | Contents |
| --- | --- |
| Document | `id`, `title`, `markdown`, `revision`, `createdAt`, `updatedAt` |
| List | Summaries, `total`, `hasMore`, and optional `nextCursor`, ordered by latest write |
| Search | Case-insensitive literal substring matches, including Chinese, with 1-based line numbers and context |

Pass opaque cursors back unchanged. Search cursors are bound to query parameters and resource revision; restart the search after a document or attachment changes. Document content and chunk indexes commit in one SQL transaction.

Pass the revision you read as `expectedRevision` when editing, or use `deleteDocument(id, expectedRevision)`. A mismatch returns a conflict: retain the draft, read again and resolve the change. Omitting the parameter changes the current version directly. Deleting a missing document returns `{ id, deleted: false }`; a stale expected revision returns a conflict.

### Size and count limits

| Item | Limit |
| --- | --- |
| Title | 512 characters |
| Markdown body | 4 MiB characters |
| ID | 256 characters, excluding NUL |
| List page | 1–100 items |
| Search page and maximum match count | 1000 |
| Search context | Up to 100 lines before and after |
| Line reads | Up to 1000 lines per call |

`getRevision()` returns the resource revision so the host can decide when to refresh.

## Attachments

```ts
const image = await knowledge.files.createFile({ name: "image.png", mimeType: "image/png", buffer });
const resolved = await knowledge.files.readFile(image.id);
const bytes = await resolved.readBuffer();
await knowledge.files.deleteFile(image.id);
```

Files allow at most 50 MiB. References retain `storage: "database"` and `spaceId` (the knowledge base UUID). HTTP uses Base64; SQL stores only metadata and checksums, while contents use private file storage. Durable upload/delete intents let background collection recover failed uploads and deleted objects. Reads verify size and SHA-256.

`readFile()` downloads once. Subsequent `readBuffer()` and `readBase64()` calls reuse the content but recheck the current binding and read authorization each time. Revocation invalidates retained handles. Configuration attachments and project-hosted files have separate read permissions and APIs.

Each Server knowledge host keeps a bounded memory cache of up to 32 MiB of Base64 attachment content, scoped to the account, consumer entry, binding version and file. Cache hits first check attachment metadata online to verify access and existence. Writes, revocation, failed reads and account changes invalidate cached content. Mutable documents, lists and search results remain online, and writes still require confirmation. Project-hosted files use conditional requests when the Server provides ETag or Last-Modified, with online authorization on every read.

## Authorization and failures

Owners manage account `read` / `write` grants. A binding cannot exceed the account grant. Registered projects also require project membership capabilities and an entry resource declaration. Changed grants, bindings or access versions invalidate old clients; reopen the entry. An administrative key cannot replace account identity.

Persistent access requires reachable Server and PostgreSQL instances. Both may run locally without internet access. Missing sign-in, declarations, bindings, grants or storage fail explicitly without falling back to local KV. There is no transaction spanning knowledge bases, business databases and runtime storage.
