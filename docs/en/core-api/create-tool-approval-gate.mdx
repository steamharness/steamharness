# createToolApprovalGate

Before a tool call, use `steamharness.createToolApprovalGate()` to check whether the tool is enabled and whether approval is required. Register Workflow tools on the selected operation and Bot tools on the executor.

An unregistered tool fails validation; a disabled tool is rejected. An enabled tool runs immediately when automatically approved. Otherwise, it follows the turn's approval policy: plan turns pause for confirmation, while build turns execute the plan the user already approved.

Ordinary Workflow runs retain the default approval requirement. The mode rules and error types are listed below.

## Signature

```ts
steamharness.createToolApprovalGate(): ToolApprovalGate
```

```ts
interface ToolApprovalGate {
  approve(
    input: ToolApprovalRequestInput,
    context: NodeContext,
  ): Promise<ToolApprovalDecision>;

  wrap<Args extends unknown[], Result>(
    name: string,
    fn: (...args: Args) => Promise<Result> | Result,
    options?: {
      label?: string;
      description?: string;
      reason?: string;
      arguments?: (...args: Args) => unknown;
    },
  ): (context: NodeContext, ...args: Args) => Promise<Result>;
}
```

## Tools Registration

Declare default policies in `tools` on the selected Workflow entrypoint or Bot executor. Runtime overrides apply only to tools registered in that execution configuration; overrides for unknown tools are ignored.

```ts
export const executor = steamharness.defineExecutor<Input, OutputPayload>({
  projectType: "workflow",
  defaultEntrypoint: "main",
  entrypoints: [
    steamharness.defineEntrypoint<Input, OutputPayload>({
      id: "main",
      title: "Full workflow",
      workflow: toolProject,
      tools: [
        {
          name: "search",
          label: "Search",
          description: "Search external sources.",
          enabled: true,
          autoApprove: false,
        },
      ],
      createInput({ args }) {
        return { query: args.join(" ") };
      },
    }),
  ],
});
```

|Field|Type|Description|
| --- | --- | --- |
| `name` | `string` |Stable tool name. Required. Empty strings are ignored.|
| `label` | `string` |Display name.|
| `description` | `string` |Tool purpose.|
| `enabled` | `boolean` |Enabled by default; defaults to `true`.|
| `autoApprove` | `boolean` |Approve automatically; defaults to `false`.|

## approve

`approve(input, context)` checks permission without invoking the business function. It returns `{ approved: true }` after approval and throws `tool_permission_denied` if the user rejects the request.

|Input field|Type|Description|
| --- | --- | --- |
| `name` | `string` |Tool name, must match the `tools` declaration of the current entrypoint or Bot executor.|
| `label` | `string` |Display label; defaults to the registered tool label.|
| `description` | `string` |Description; defaults to the registered tool description.|
| `reason` | `string` |Reason for the call.|
| `arguments` | `unknown` |The parameter snapshot of this call is written to the approval request metadata.|

## wrap

`wrap(name, fn, options)` returns a function that checks approval before calling `fn`. Pass a `NodeContext` as its first argument; the remaining arguments are forwarded to the original function.

```ts
const approval = steamharness.createToolApprovalGate();

const searchWithApproval = approval.wrap(
  "search",
  async (query: string) => {
    return fetchSearchResult(query);
  },
  {
    label: "Search",
    reason: "External research is needed before answering.",
    arguments: (query) => ({ query }),
  },
);

const result = await searchWithApproval(context, input.query);
```

## Running behavior

|Status|Behavior|
| --- | --- |
|Tool not registered|Throws `HarnessError` of type `input_validation`.|
|Tool is disabled|Throws `HarnessError` of type `tool_permission_denied`.|
| `autoApprove: true` |Returns `{ approved: true }` without a waiting request.|
|Requires approval, and the turn is in plan mode|The `tool-approval` request is created and the running status becomes `waiting_for_input`.|
|Requires approval, but the turn is in build mode|Returns `{ approved: true }` without a waiting request.|
|User Approval|Restore the same `runId`, return `{ approved: true }`, and continue calling the tool.|
|User Rejected|Throw `tool_permission_denied`.|

The Agent runtime sets `context.toolPermissions.requiresUserApproval` for each turn: `true` for plan and `false` for build. Runs outside the Agent, including ordinary Workflow runs and callers without a mode, retain the default `true` and follow `autoApprove`.

A disabled tool is rejected in every mode. This setting controls whether an enabled tool pauses for confirmation.

Approval uses the same wait/resume protocol as `steamharness.createUserInputNode()`. The default request ID includes the workflow, run ID, and tool name; request `params` includes the boolean field `approved`.

CLI Web displays a dedicated approval view with the tool ID and `arguments` snapshot. Choose "Approve and continue" or "Reject and end". There is no generic boolean switch, and pressing Enter does not implicitly approve the tool.

Bot stores tool enablement and automatic approval per conversation. Returning to a conversation restores its Tools Permissions state; later runs and approval recovery use that conversation's policy snapshot.

New conversations, or those without their own policy, use executor `tools` defaults. They do not inherit project-level overrides or another conversation's policy. Ordinary Workflow runs use project-level tool policies.

## CLI Recovery

The local CLI returns a `waiting_for_input` report instead of opening an approval dialog. Read its request ID, then resume with the same `runId` and an answer in `--resolved-user-inputs-json`:

```bash
steamharness json . -- --message "run tool"
steamharness json . \
  --run-id <run-id> \
  --resolved-user-inputs-json '[{"requestId":"<request-id>","nodeName":"tool-approval","values":{"approved":true},"submittedAt":"2026-07-08T00:00:00.000Z"}]' \
  -- --message "run tool"
```

CLI Web and local hosts pass the run's tool-policy snapshot through `--tool-permissions-json`. Supply it during manual CLI debugging only when you need to reproduce a host's enablement or automatic-approval policy.

## Error

|Situation|Error Type|Description|
| --- | --- | --- |
|Tool name is empty| `input_validation` |`name` must be a non-empty string.|
|Tool not registered at `executor.tools`| `input_validation` |Only declared tools can be approved.|
|Tool disabled by policy| `tool_permission_denied` |The current run does not allow the tool to be called.|
|User Rejected Approval| `tool_permission_denied` |On recovery `values.approved !== true`.|
|No user input runtime and approval required| `user_input_required` |The host has no input handler for pausing and resuming approval.|
