# 数据库与会话

业务关系库、知识库和对话历史使用不同的存储与授权。创建项目或会话不会自动建业务数据库；需要业务表时，先申请资源、迁移模型并绑定入口。

## 业务关系表

1. 在入口的 `steamharness.database.ts` 中声明别名，在 `steamharness.schema` 中定义模型。
2. 将所需别名列入入口声明的 `databases`。
3. 在 Server 绑定账号、项目、入口和别名，再用生成的描述符连接。

业务数据库 ID 和凭据不写入项目配置。

```ts
import { main } from "./dist/steamharness/generated/database/node/index.js";

const db = await context.databases.connect(main);
const users = await db.user.findMany({ orderBy: { id: "asc" } });
```

每个资源是独立 PostgreSQL database。A、B 项目都定义 `User` 表时，绑定不同资源即可隔离结构和数据；只有显式绑定相同 UUID 才共享。事务限定同一客户端，不提供跨库原子提交。详见 [数据库 API](/core-api/database)。

## 聚合内调用

```ts
const result = await context.entries.get("jobs")
  .runEntrypoint("refresh", ["--limit", "10"]);
```

只可调用已注册的 Workflow 入口。宿主保留用户、取消信号和工具权限，加载目标配置与绑定并再次鉴权。调用方不会因此获得目标入口的数据库句柄。

## 知识库与附件

使用 `context.knowledgeBases.get("docs")` 访问文档及其 `files` 附件。知识库使用独立资源、账号授权和入口绑定，无需业务项目定义 schema。文件字节保存在私有文件存储，元数据和版本保存在关系表；业务表只保存引用。详见 [知识库 API](/core-api/knowledge-documents)。

## Conversation 与运行存储

会话、消息、输入队列、草稿、Run、用量与 Agent 检查点默认保存在宿主本地 SQLite，按项目、入口和 conversationId 隔离。运行历史不需要业务库权限，也不会为每个会话创建远程数据库。

`context.conversation.getValue/setValue/setTitle/appendMessage` 操作当前会话；这些方法与业务模型客户端独立。配置修改从下一次执行生效，恢复审批必须匹配当前项目和入口。

本地持久历史不要求平台登录或网络连接；系统 AI 和业务资源仍按各自权限校验。可信宿主可显式选择 Server 仓储，或用 `copyRuntimePersistence` 在会话空闲时后台复制到空云端目标。它是按需快照备份，不是持续同步；附件与工作区文件独立备份。已有云端和旧本地记录保留，不自动读取、迁移或双写；不重新引入 KV 或 PersistentValue。详见[运行存储](/core-api/runtime-storage)。

## 本地 Conversation 入口控制

CLI Web / Studio 的聚合宿主提供 `context.entries.conversations.get(entryId)`。目标必须是已登记的 Conversation，所有操作复用原生控制器、执行 owner、持久输入队列及 Core 历史，不创建第二份执行会话：

```ts
const bot = context.entries.conversations.get("assistant");
const receipt = await bot.submit({
  conversationId: "support-room", requestId: "stable-request-id", text: "整理待办",
});
const snapshot = await bot.snapshot(receipt.conversationId);
// 其它操作：list()、resolveInput({ conversationId, messageId, requestId, values })、
// cancel({ conversationId, requestId })、resumeQueue({ conversationId, requestId })。
```

### 提交与恢复队列

`submit` 将输入持久化后返回 `{ conversationId, requestId, messageId, status }`，无需等待模型完成。省略参数时复用会话参数与宿主默认模型。

| 条件 | 结果 |
| --- | --- |
| 相同会话、请求 ID 和内容再次提交 | 不重复执行 |
| 相同会话和请求 ID，但内容不同 | 拒绝提交 |
| 执行失败、停止或重开 | 保留输入队列，显式 `resumeQueue` 后继续 |
| `conversation.recovery: { enabled: true, startup: "manual" }` | 重开后的未完成轮次也等待恢复 |
| 默认 `startup: "automatic"` | 沿用自动恢复行为 |

### 消费会话快照

快照包含 `ownerId`、递增的 `revision`、消息、待确认请求、运行状态和 FIFO 队列位置。消费者应拒绝旧 revision；owner 变化后，丢弃已退休 owner 的结果。

投影不含宿主凭据、用户设置或运行参数。业务聊天可以保存投影和回执，但执行历史仍以 Core 为准。

### 识别调用者与宿主

`context.entries.caller` 提供可信的直接来源 `{ entryId, conversationId?, runId? }`，由宿主或 Core 设置。用它和受控的会话关联识别 Bot，不要相信业务参数自报的身份。

调用保留用户、项目、权限和取消信号，并重新检查目标授权。单独命令运行和 Server 静态预览没有执行宿主，会返回 `ENTRY_RUNTIME_UNAVAILABLE`；Server 不执行项目代码。
