# 验证项目与改动

项目测试先验证输入、输出和错误路径，再验证宿主界面与外部服务。使用隔离的示例数据，明确记录哪些检查实际执行过。

## 检查自己的项目

在项目根目录执行：

```sh
pnpm exec steamharness check .
pnpm exec steamharness structure .
pnpm exec steamharness run .
pnpm exec steamharness json .
```

聚合项目逐个验证 Workflow、Conversation 和 Kanban 入口。结构检查不执行用户代码；运行成功后，还需确认页面或调用方实际收到了预期结果。

## 测试分层

| 层次 | 验证内容 |
| --- | --- |
| 纯逻辑 | 参数解析、类型转换、业务计算、错误条件 |
| 执行器 | 入口选择、参数、输出、等待输入与取消 |
| 资源 | 授权、绑定、并发版本、断连和存储失败 |
| 宿主 | 真实页面、输出顺序、队列、恢复和中英文显示 |

模型测试先用确定性的测试 Provider，文件使用固定样本。真实模型、数据库、外部进程和可见窗口需要单独的验证环境与明确启用。

## 给新代码补测试

- 节点与执行器：覆盖正常结果、校验失败、取消和恢复。
- 配置与数据：覆盖版本冲突、权限撤销以及失败后草稿保留。
- 页面：覆盖加载、空状态、失败、禁用与关键交互。
- 异步会话：用请求或消息 ID 匹配完成，不能依赖数组最后一项。

## 示例项目的文件

| 文件 | 用途 |
| --- | --- |
| `__fixtures__/smoke.json` | 输入、会话 ID、预期输出和所需节点 |
| `__snapshots__/structure.json` | 精简的入口、参数、节点和分支结构 |
| `__tests__/` | 项目逻辑与工具测试 |

依赖真实服务的示例应注明前提和单独运行方式。跳过的用例保留原因，不把静态校验作为实际服务验证。

## 修改 SteamHarness 源码

以下命令从开源仓根目录执行，只运行改动涉及的包：

| 范围 | 检查 |
| --- | --- |
| SDK | `corepack pnpm -C harness typecheck`、`corepack pnpm -C harness test`、`corepack pnpm -C harness build` |
| CLI | `corepack pnpm -C cli typecheck`、`corepack pnpm -C cli test` |
| Server 与 Web | `corepack pnpm -C server typecheck:all`、`corepack pnpm -C server test`、`corepack pnpm -C server build:all` |
| Studio 扩展 | `npm --prefix studio run check`、`npm --prefix studio run build:extension` |
| 文档内容 | `node docs/scripts/validate-docs.mjs`、`node --test docs/scripts/__tests__/*.test.mjs` |

Server 集成测试使用隔离的 PostgreSQL 容器，执行前检查 Docker。共享接口修改后还需验证消费它的 SDK、CLI、Server 或 Studio；站点构建由消费文档内容的工作区完成。
